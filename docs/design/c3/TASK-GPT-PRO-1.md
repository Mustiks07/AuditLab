# GPT Pro 1 — реализовать дизайн AuditLab C3

Ты отвечаешь за реализацию выбранного дизайна AuditLab. Репозиторий: https://github.com/Mustiks07/AuditLab. Интегратор — GPT Pro 2. Пользователь выбрал светлый C3; тёмные A/A2 и прежний B не использовать.

## Начало работы

1. Работай в отдельном клоне/worktree, сохрани чужие изменения. Выполни fetch, изучи актуальный main и открытые PR, особенно затрагивающие консоль. Не откатывай новые исправления к версии пакета.
2. Создай свою ветку `feature/workspace-c3` от актуального `origin/main`. Если уже существует — изучи и продолжи её, без force push.
3. Забери `docs/design/c3` из ветки `design/c3-handoff` (например, `git restore --source=origin/design/c3-handoff -- docs/design/c3`). Не переключай реализацию на старую базу пакета.
4. Прочитай README, DESIGN, DATA-AND-COPY, ACCEPTANCE в пакете, затем `docs/SPEC.md`, `docs/INTERFACES.md`, `docs/TEAM.md`, текущую задачу консоли и код `web/`. Визуально открой PNG и HTML-образец.

## Главная задача

Собрать работающий профессиональный интерфейс, максимально близкий к C3 по композиции, масштабу, типографике, пространству и деталям. Это полноценная среда работы с проверками, а не лендинг и не специальный экран жюри.

Сначала закончи ОДИН главный экран: «Рабочая область». Пользователю показывать один актуальный скриншот этого экрана за итерацию, без коллажей из двух/трёх вариантов. Его композиция уже выбрана: боковая навигация, заголовок и поиск, продолжение проверки, небольшая карточка сравнения, последние запуски. Не перерисовывай дизайн произвольно и не добавляй маркетинговые блоки.

Когда главный экран совпадает с ориентиром, проведи тот же стиль через существующие рабочие маршруты: список запусков, расследование и документы, сравнение, повтор, изменение факта и пересчёт. Существующие функции должны сохраниться. Новые страницы рисовать отдельно пачкой не требуется. Итог проверять как единый сценарий.

## Обязательное уточнение пользователя о языке

На обычных экранах не должно быть `demo/003d1`, хешей, `run_id`, `episode_id`, путей, JSON, названий Python-модулей, `reconcile`, `infrastructure_error`, «консоль жюри», постоянных надписей «только демо» / «синтетические данные». Используй человеческие названия: «Сверка платежей», «Частичное распределение», «Платёж», «Не удалось выполнить проверку».

Не удаляй исходные идентификаторы из API, URL, расчётов, связи документов и выгрузок: они нужны воспроизводимости. Диагностику можно скопировать или скачать отдельным действием без печати сырого кода на обычном экране. Происхождение набора доступно в «О данных», без постоянного служебного баннера. Не заявляй, что тестовый набор — реальные клиенты, что запуск подтверждён без проверки или что F1 — конкурсный балл. См. DATA-AND-COPY.

## Реализация

- Сохрани React/TypeScript/Vite и текущие контракты. Начальные точки: `web/src/App.tsx`, `views/RunsList.tsx`, `components.tsx`, `styles.css`, `api.ts`, `format.ts`.
- Выдели tokens, AppShell, Sidebar, WorkspaceHeader, ContinueReview, PairPreview, RunsTable и состояния. Не делай один гигантский JSX и не ставь новую UI-библиотеку ради базовых компонентов.
- Перенеси локальный Inter с лицензией. Размеры и цвета зафиксированы в DESIGN/tokens; допустима аккуратная доводка по реальному рендеру.
- Все кнопки должны выполнять настоящие действия. «Открыть запуск» — открыть выбор существующего запуска, не создать новый и не притвориться загрузкой файлов. Новые действия вводи только с реальной поддержкой.
- Поиск, фильтры, выбор строки, продолжение работы, документы и сравнение должны работать с реальными данными. Не хранить в production образцовые даты, суммы или список компаний.
- Избранное можно хранить локально как ID запусков с версионированным ключом; недоступные записи обрабатывать честно. «Документы» ведут к документам выбранного запуска, при отсутствии выбора сначала выбор запуска. Сравнение предлагает существующие пары, при отсутствии показывает пустое состояние. Никаких ссылок-заглушек.
- Поиск по Ctrl/Cmd+K, видимый focus, Escape для модальных окон, работа клавиатурой, адаптивность и prefers-reduced-motion обязательны.
- Общую таблицу не сужать до микрошрифта. На телефоне перестроить строки и навигацию. Суммы в разных валютах не суммировать.
- Полноценные состояния: загрузка, пустой список, нет совпадений, недоступный сервер, отсутствующий документ/запуск, неподключённая сверка, незавершённый запуск. Ошибки объяснять человеку.

## Изображения и детали

Простые иконки — единый SVG-набор, аккуратно выполненный знак AuditLab, без эмодзи. Если сложную нужную иллюстрацию/фото нельзя сделать красиво вектором, используй генерацию изображений и приложи исходник, промпт, локальные файлы. При отсутствии инструмента сообщи конкретную потребность интегратору; не заменяй её неудачной геометрией. На утверждённом рабочем экране дополнительная иллюстрация не требуется. Нельзя встраивать растровый текст кнопок/таблиц или весь макет картинкой.

## Проверка и сдача

Запусти команды из ACCEPTANCE. Проверь реальные экраны в браузере на 1440×960, 1280×800 и 390×844, клавиатуру, денежное форматирование, все действия, отсутствие внешних запросов и сохранение прежних сценариев. Сопоставь реальный главный экран с C3 и HTML-образцом, исправь визуальные отклонения. Не ограничивайся успешной сборкой.

Создай PR в main. В описании: что изменилось, исходный/проверенный SHA, команды и результаты, ссылка на ОДИН основной реальный скриншот, дополнительные разрешения/состояния в отдельной папке evidence, известные ограничения. Отдельно укажи, что проверено на настоящем API, а что только на тестовых ответах. Не объявляй все сценарии проверенными по одной картинке. Слияние выполняет интегратор; сам main не меняй.

Не назначай работу Claude 2: пользователь даст ему отдельную задачу. Если нужна координация общих файлов, сначала опиши границу в PR/отчёте интегратору.

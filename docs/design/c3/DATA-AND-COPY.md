# Источники данных и продуктовый язык

## Последнее требование пользователя

Обычный интерфейс должен выглядеть и говорить как законченный продукт. Убрать из видимого основного пути технические ID/пути, внутренние имена, словечки «demo», постоянные пометки «синтетические данные» и «только демо». Это изменение представления, а не изменение фактов или удаления происхождения данных.

| Внутреннее значение | Пользовательское представление |
|---|---|
| `reconcile` | Сверка платежей (проверить смысл конкретной политики; описание возможностей отдельно) |
| `TRAIN-S02-reconcile`, `S02` | Частичное распределение — только для известного именованного примера, не по совпадению суффикса |
| `TRAIN-S01-reconcile`, `S01` | Полное распределение — только для известного примера |
| Неизвестное имя политики | Пользовательский аудитор; исходное имя в выгрузке |
| Длинное название из генератора | Короткий человеческий alias + период; полный ID сохраняется в модели |
| `run_id`, `episode_id`, хеши | Не выводить текстом в UI; оставлять в маршрутах, данных и диагностической выгрузке |
| `public/payments.json`, `payments/D9` | Платежи / Платёж; различать записи человекочитаемым названием из данных, без выдуманных номеров счетов |
| `infrastructure_error` | Не удалось выполнить проверку |
| `truncated`, `aborted` | Проверка не завершена / Проверка прервана |
| `demo/...`, `auditlab.verifier` | Ни в заголовке, ни в tooltip обычного экрана; техническая выгрузка отдельно |
| «Консоль жюри» | Рабочая область / AuditLab |
| «Только демо», служебный баннер | Убрать из обычного пути. Происхождение и ограничения набора — в отдельном «О данных». |

Словарь должен быть единым; не делать replace по всем строкам API. Сохранить уникальность алиасов при одинаковых компаниях/периодах: например, «Компания B · проверка 2», устойчиво по run_id. Не путать alias с юридическим названием организации. Не менять сырые данные на «красивые» значения.

В «О данных» можно честно объяснить происхождение открытого набора и его ограничения нормальным языком. Основной экран не обязан постоянно показывать этот текст. Нельзя называть полученные на образцах результаты результатами аудита реального клиента или официальной конкурсной оценкой.

## Откуда брать содержимое главного экрана

- `api.runs()` → список/метаданные/пары. Не содержит всех сумм и статусов независимой сверки.
- `api.run(selectedId)` → данные выбранного запуска и его выводы. Загрузить один выбранный запуск, кешировать, отменять/игнорировать устаревший ответ при быстром переключении; не делать N запросов для N строк ради отображения карточки.
- Компания и период → реальные метаданные. Отсутствующее поле не заменять вымышленным ноябрём 2026.
- Сумма → выбранный finding + currency; формула → его derivation. Не выводить одинаковую формулу для FX и распределения платежа.
- Число документов/проводок → snapshot.tables только при однозначной семантике. Не копировать 240/76 из рисунка.
- Контрольная пара → pair_id/pair_role или связь parent/child. Времена → опубликованный факт/изменение, а не ID или строковый шаблон. Указать фактическую временную зону и исключительную верхнюю границу в подробностях.
- Продолжение → последнее просмотренное доступное ID. Удалённый экспорт не ломает home; выбрать доступный или показать пустое состояние.

## Три разные проверки — не склеивать

1. Статус выполнения: `run.status`. `completed` означает завершение, а не качество ответа.
2. Расчёт консоли по публичным документам: `derivation`, `console_agrees`, полнота/доступность ссылок. Только если derivation существует, result не null, валюта совпадает, ссылки доступны и расчёт согласуется, допустима подпись «Подтверждено по документам». Если нет уверенности — «Расчёт требует проверки». Сохранять пояснение, что проверялось именно в консоли.
3. Независимый verifier: `finding.verifier.connected`, `agrees === true`, `currency_matches === true` плюс опубликованный результат. Подпись «Независимо подтверждено» допустима только при подтверждённых условиях; undefined/null не равны true. Если валюта не опубликована, не угадывать её. `verdict.matched` оценщика и `console_agrees` не являются заменой verifier.

На карточке можно показать один краткий достоверный итог, а в подробностях различать все три источника. Ни отсутствие ошибок API, ни ненулевой reward, ни пустой список выводов не подтверждают отсутствие финансовых ошибок.

Для таблицы безопасная подпись при completed + findings=0: «Без выводов». «Без расхождений» применять только при наличии данных, подтверждающих именно сверку. Это намеренное уточнение к исходной картинке C3. null/undefined findings → «Результат недоступен», не ноль. При сбое показывать сбой раньше количества findings. Награда null → «—», не 0; инфраструктурные ошибки не участвуют в средних как нулевые награды.

## Деньги и доказательства

Числа в API — minor units. Использовать существующий money и currency_exponents. 2 000 000 KZT minor = 20 000,00 ₸; JPY exponent 0, KWD exponent 3. Не делить всё на 100, не округлять для красоты, не складывать разные валюты, не превращать неизвестную сумму в ноль. Отсутствующая разрядность — понятное сообщение о невозможности форматирования + доступная диагностическая выгрузка.

Текстовые доказательства должны открывать ту же исходную запись; alias не меняет ключи. Полный raw JSON/CSV не показывать по умолчанию и не выдавать за основной документ. Если он нужен специалисту — экспорт исходного файла, отдельная диагностическая функция, не обычная карточка.

## Ошибки без кодов в UI

Показывать понятную причину, следующее действие и при необходимости «Скопировать диагностику»/«Скачать отчёт». Нельзя непосредственно вставлять Error.message или opError(), если там сырой code/path. Не терять исходную причину в логах. Не обещать автоматическую повторную попытку, если она не реализована. Не делать обработку ошибок фиктивным успехом.

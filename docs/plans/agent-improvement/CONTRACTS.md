# Контракты новой итерации, проект версии 1

Это новые предлагаемые контракты, не описание уже существующих функций. Перед
реализацией сверить с принятым main, переиспользовать имеющиеся форматы и зафиксировать
JSON Schema и пример каждого артефакта. Корневые зависимости меняет интегратор.

## Владение

- GPT 1: `auditlab/research/curriculum/`, соответствующие тесты и документация.
  Изменения существующего generator — отдельный явно обозначенный PR с регрессиями.
- Claude 1: `auditlab/research/agents/`, `auditlab/research/training/`, сетевой мост,
  тесты. Изменения runner/evaluator — через согласованный контракт, не обход sandbox.
- Claude 2: `tests/research_acceptance/`, `docs/research/agent-generalization/`;
  независимые вычисления отдельно от тестируемой реализации.
- Claude 3: новые экраны исследования и `auditlab/demo` read-only представление
  артефактов. Согласовать общие frontend-файлы после завершения дизайна GPT 1.
- Интегратор: `auditlab/research` общая CLI/схемы, locks, CI, release и общая отчётность.

## Предлагаемые артефакты

Во всех JSON: `schema_version`, `artifact_id`, `source_sha`, `protocol_id`.
Числа конечные; счётчики целые неотрицательные; отсутствие результата — null и причина,
не ноль. Хеши содержимого фиксируются после записи; приватные данные не публикуются
в UI/API по умолчанию. Идентификаторы не заменяются человеческими именами в протоколе.

| Артефакт | Обязательные сведения |
|---|---|
| experiment.json | Разбиение и его хеш, модели/параметры/промпты, варианты, повторы, бюджеты, лимиты времени, правила анализа |
| candidate.json | Генератор/профиль/config/seed на доверенной стороне, family_id, split, parent, мутация, хеши snapshot, история поиска |
| validation.json | Проверка исходной книги, независимый расчёт, совпадение truth, доступность доказательств, допустимая по бюджету траектория свидетеля, причины отказа |
| attempt.json | agent/model/prompt hashes, episode hash, repetition, timestamps, действия и наблюдения, финальный ответ, статус, токены/стоимость/время, ссылки на закрытую оценку |
| failure.json | Проверяемый критерий ошибки, все исходные и повторные попытки, частота и неопределённость, альтернативные объяснения |
| reduction.json | Исходный и сокращённый snapshots, преобразования, независимая валидация и повторные попытки до/после |
| curriculum.json | Семейства/разбиение, происхождение и фильтрация примеров, хеши, поддерживаемый формат экспорта обучения |
| training.json | Исходная модель, данные, настройки, бюджет/факт, job/checkpoint identity, результат/ошибка; отдельно kind=weights/prompt/few_shot |
| comparison.json | Полная выборка, варианты, метрики и знаменатели, парные интервалы, пропуски, затраты и ссылки на исходные попытки |

Итоговые статусы проверки: `passed`, `failed`, `not_checked`. Операционные статусы
попыток отделены: завершена, timeout, ошибка провайдера, некорректный ответ, остановка
по бюджету. Не объявлять финансовый результат для попытки, которую нельзя оценить.

## Предлагаемые команды

Общий CLI проектируется интегратором как `python -m auditlab.research ...`:
`validate-plan`, `run`, `search`, `reduce`, `build-curriculum`, `train`, `compare`, `replay`.
Это спецификация будущего CLI; пока команды не реализованы. Все используют версионный
конфиг, manifest и новые каталоги вывода; resume не дублирует оплаченные вызовы или
задания обучения. Нужны dry-run, ограничение расходов и корректное сохранение при сбое.

Агент получает observation, состояние своих заметок и допустимые инструменты;
возвращает только разрешённое действие. Заметки — факты/ссылки/проверяемые гипотезы,
не запрос скрытых цепочек рассуждения модели. Локальный валидатор может проверять
структуру и уже полученные публичные ссылки; он не вычисляет ответ по truth и не
приписывает модели собственное исправление финансового вывода.

Поиск использует только training/search разделы. Сокращатель принимает независимый
валидатор и предикат повторяемого сбоя, не просто наличие старого ошибочного ответа.
UI читает только разрешённую проекцию артефактов, никогда ключ API/приватный каталог.

## Стыки для параллельной реализации

Сначала интегратор фиксирует JSON Schema версии 1.0 и golden JSON для таблицы выше.
До их появления исполнители используют эти поля и публикуют примеры request/response
в своих PR; не создают конкурирующие версии общей CLI и общих схем.

- Claude 1 предоставляет агентский интерфейс: `start(public_observation, agent_config)`,
  `act(public_observation) -> official_action`, `close()`. Учёт времени/токенов/стоимости
  хранится отдельно от official_action. Controller сам вызывает step; модель не имеет
  файлового доступа к каталогу эпизода. Следующее act получает настоящий ответ среды.
- Интегратор предоставляет `run_attempt(snapshot_ref, agent_config, protocol_config,
  output_dir) -> attempt_ref`. Артефакты неизменяемы после финализации, повтор имеет новый
  attempt_id. До подключения настоящего executor допускается только помеченный test double.
- GPT 1 предоставляет `search(search_config, run_attempt, validate_candidate, output_dir)`
  и `reduce(candidate_ref, failure_predicate, validate_candidate, output_dir)`;
  callbacks позволяют подключить независимую проверку и настоящий runner без импорта
  реализации Claude 2 и без передачи truth агенту. У поиска явный предел кандидатов,
  повторов и расходов; сохраняются все отклонённые/принятые кандидаты и причины.
- Claude 2 предоставляет `validate_candidate(snapshot_ref, protocol_config) -> validation`
  и `compare_experiment(experiment_ref) -> comparison`. Его эталон не импортирует расчёты
  generator/matcher/verifier; сравнение с ними выполняется после собственного ответа.
- GPT 1 экспортирует train/dev curriculum; Claude 1 реализует `train(training_config,
  curriculum_ref, output_dir) -> training_ref`. Платный job создаётся только при валидном
  бюджете/доступе; resume использует сохранённый job ID и не создаёт дубликат.
- Claude 3 читает артефакты через серверную проекцию. Запуск/остановка — через controller
  интегратора. Источник данных, статус и причина отсутствия результата сохраняются;
  browser не вычисляет финансовый итог или новые агрегатные метрики самостоятельно.

Это логические сигнатуры стыков; конкретные Python-типы фиксируются общей схемой.
Нет нужды ждать целого чужого PR: сначала публикуются минимальные исполняемые стыки
и contract tests, затем полная реализация. При этом итоговая сдача каждой роли включает
весь выданный объём, а не только заглушки или описание намерений.

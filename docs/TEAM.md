## Как начать

Из клона репозитория выполни `git fetch origin`, затем `git switch ИМЯ_ВЕТКИ`. Прочитай свой файл задачи, ТЗ и INTERFACES.md. Первый PR должен дать проверяемый сквозной результат в своей области. При продолжении работы из прежней ветки сначала добавь принятые изменения main. У каждого рабочего аккаунта своя ветка. Это логические роли: один GitHub-профиль может работать в нескольких отдельных сессиях.

## Параллельная работа

GPT Pro 1 выпускает генерацию пары и публичные инструменты; Claude Pro 1 параллельно испытывает оценщик на тестовых снимках; Claude Pro 2 фиксирует собственные расчёты по public/; Claude Pro 3 начинает с открытого, помеченного примера журнала. GPT Pro 2 сводит потоки и запускает общие тесты. Порядок слияния определяется готовностью контрактов: изолированные изменения допускаются параллельно, интеграционный прогон — после подключения настоящих реализаций.

Общие схемы, корневые версии зависимостей и выпускные команды координируются с GPT Pro 2. Для изменения чужого интерфейса опиши требуемое изменение и пример запроса/ответа в PR. В main интегратор использует проверенные PR. Статус роли не означает, что отдельная внешняя сессия GPT или Claude уже запущена.

## Проверки PR и зависимости

Базовая среда интеграции: Python **3.11.14**, пока только стандартная библиотека.
`requirements.lock` фиксирует отсутствие внешних пакетов текущего среза, а не
готовность автономного релиза. Версии DuckDB, Pydantic, pytest/Hypothesis,
FastAPI и фронтенда добавляются при приёмке соответствующих веток: автор PR
указывает точные версии, транзитивные зависимости, совместимость с Python 3.11
и способ офлайн-поставки. Интегратор обновляет общий lock и проверяет чистую
установку. Разрозненные ограничения версий без общего lock не считаются релизом.

В каждом PR нужны ссылка на свою Issue, актуальный SHA, команды, фактические
результаты и пропуски, пример входа/выхода изменённого интерфейса. Интегратор
проверяет текущий head PR и его совместимость с текущим main в отдельном checkout,
запускает `python run.py verify` и тесты зоны владельца. При новом коммите или
движении базы проверка обновляется. Слияние выполняется только для проверенного
SHA; регрессия возвращается с входом, ожидаемым/фактическим результатом и командой.
Зелёный CI первого среза означает отсутствие регрессий в доступных тестах;
готовность всего релиза проверяется отдельно через `--require-complete`.

Тесты компонента публикуются в его каталоге tests/<компонент>/ с unittest-совместимой
точкой входа. Если компонент использует pytest, его PR добавляет точную зависимость
и адаптацию общего запуска; пустая discovery не считается успешной проверкой.

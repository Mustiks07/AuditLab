# Работа пяти аккаунтов

Цель выпуска — подготовить AuditLab к победе по опубликованным критериям кейса.
Рабочие условия готовности: корректные финансовые данные и награда, фактическая
изоляция, автономная поставка, 80 внутренних результатов и 20 пар с воспроизводимыми
свидетельствами. Место определяет жюри; число unit-тестов не превращается в конкурсные баллы.
Обнаруженные дефекты исправляются до финальной приёмки, а оставшиеся ограничения
отмечаются явно. Эти пять ролей — рабочие потоки; состав команды людей указан отдельно.

| Аккаунт | Ветка | Зона ответственности |
|---|---|---|
| GPT Pro 1 | `feature/simulator` | [Симулятор, публичные инструменты и обучающие наборы](tasks/gpt1.md) |
| Claude Pro 1 | `feature/evaluator-runner` | [Оценщик, контракт reset/step и изоляция раннера](tasks/claude1.md) |
| Claude Pro 2 | `feature/independent-verifier` | [Независимая финансовая сверка и парные испытания](tasks/claude2.md) |

## Как начать

После нормализации авторства начинай в **новом клоне**: `git clone https://github.com/Mustiks07/AuditLab.git`, затем `git switch ИМЯ_ВЕТКИ` и `git merge origin/main`. Старый клон сохрани, если в нём есть неопубликованные изменения; перенеси их отдельным patch после просмотра, не сливай прежнюю переписанную историю обратно. Прочитай свой файл задачи, полное ТЗ и INTERFACES.md. У каждого рабочего аккаунта своя ветка. Это логические роли: один GitHub-профиль может работать в нескольких отдельных сессиях.

## Параллельная работа

GPT Pro 1 выпускает генерацию пары и публичные инструменты; Claude Pro 1 параллельно испытывает оценщик на тестовых снимках; Claude Pro 2 фиксирует собственные расчёты по public/; Claude Pro 3 начинает с открытого, помеченного примера журнала. GPT Pro 2 сводит потоки и запускает общие тесты. Порядок слияния определяется готовностью контрактов: изолированные изменения допускаются параллельно, интеграционный прогон — после подключения настоящих реализаций.

Общие схемы, корневые версии зависимостей и выпускные команды координируются с GPT Pro 2. Для изменения чужого интерфейса опиши требуемое изменение и пример запроса/ответа в PR. В main интегратор использует проверенные PR. Статус роли не означает, что отдельная внешняя сессия GPT или Claude уже запущена.

## Проверки PR и зависимости

Базовая среда интеграции: Python **3.11.14**. `requirements.in` объединяет
DuckDB **1.1.3** и принятые версии из `web/requirements-demo.txt`;
`requirements.lock` содержит точные транзитивные версии и хеши дистрибутивов.
Обновление: `uv pip compile requirements.in --python-version 3.11.14 --generate-hashes --output-file requirements.lock`.
Этот lock ещё не означает готовность автономного релиза. Для новых пакетов автор PR
указывает точные версии, транзитивные зависимости, совместимость с Python 3.11
и способ офлайн-поставки. Интегратор обновляет общий lock и проверяет чистую
установку. Разрозненные ограничения версий без общего lock не считаются релизом.

В каждом PR нужны ссылка на свою Issue, актуальный SHA, команды, фактические
результаты и пропуски, пример входа/выхода изменённого интерфейса. Интегратор
проверяет текущий head PR и его совместимость с текущим main в отдельном checkout,
запускает `python run.py verify` и тесты зоны владельца. При новом коммите или
движении базы проверка обновляется. Слияние выполняется только для проверенного
SHA; регрессия возвращается с входом, ожидаемым/фактическим результатом и командой.
Зелёный CI первого среза означает отсутствие регрессий в доступных тестах;
готовность всего релиза проверяется отдельно через `--require-complete`.

CI сохраняет checkout context и проверяет связь всех результатов с head/base.
Перед merge интегратор заново сверяет их с GitHub по [инструкции приёмки](release/PR_REVIEW.md).

Тесты компонента публикуются в его каталоге tests/<компонент>/ с unittest-совместимой
точкой входа. Если компонент использует pytest, его PR добавляет точную зависимость
и адаптацию общего запуска; пустая discovery не считается успешной проверкой.

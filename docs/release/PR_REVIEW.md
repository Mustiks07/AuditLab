# Приёмка PR интегратором

Автор привязывает PR к Issue и описывает воспроизводимый пример, изменение
контракта/версий, команды проверок и то, что осталось «не проверено».
Общие зависимости меняет интегратор; результаты из старого checkout не переносятся
на новый коммит без повторной проверки.

## Проверка точной версии

CI сохраняет в `verification-<checkout SHA>`:

- `review-context.json`: чистый checkout, tree SHA, head/base и реальные родители
  синтетического merge-коммита GitHub;
- `ci/report.json`: восемь комплектов тестов с числом запусков и отдельными test IDs;
- `review-receipt.json`: результат сверки версий, отсутствие пропусков и SHA-256 отчёта.

Перед слиянием получить **текущие** head и base через GitHub, например:

```bash
gh pr view NUMBER --repo Mustiks07/AuditLab --json headRefOid,baseRefOid,url
```

Скачать артефакт успешного PR workflow именно для рассматриваемой версии.
Из корня доверенного checkout интегратора выполнить, подставив полученные SHA:

```bash
python tools/review_evidence.py check \
  --context /path/to/artifact/review-context.json \
  --report /path/to/artifact/ci/report.json \
  --expected-head FULL_CURRENT_PR_HEAD \
  --expected-base FULL_CURRENT_MAIN_SHA \
  --output artifacts/pr-review.json
```

Новый head или base отклоняет старый отчёт. Если main изменился, обновить ветку
из main и дождаться нового PR workflow; простой повтор старого event может
сохранить прежнюю базу. Повторно сверить оба SHA непосредственно перед слиянием.
API merge передавать `expected_head_sha`; этот параметр сам по себе не фиксирует
base. Слияния выполняются последовательно одним интегратором.

Код 0 означает, что все перечисленные тесты выполнены и соответствуют этим SHA.
Он не удостоверяет критерии Issue, независимость финансовой проверки или
безопасность изменений самого CI/checker. Их diff, тестовые примеры, совместимость
и зелёный frontend job проверяются отдельно. Такой отчёт не является криптографической
аттестацией против автора, изменившего workflow или сами тесты.

## После принятия компонентов

На `integration/release` собрать полный комплект, выполнить на свежем втором хосте
20 снимков, 4 × 20 запусков и 20 пар. Проверка свидетельств:

```bash
python tools/check_rehearsal_evidence.py \
  --results /path/to/results --bundle /path/to/bundle \
  --expected-revision FULL_TESTED_SOURCE_SHA --output artifacts/rehearsal-review.json
```

Сверяются SHA исходников, отчёта и комплекта, хеши четырёх payload-файлов, image IDs,
полнота запусков и фактические ограничения контейнеров. Этот checker подтверждает
внутреннюю репетицию; полный `run.py verify --suite rehearsal` сохраняет exit 2,
пока обязательные пункты приёмки не подтверждены. Незнакомый с проектом человек
получает тот же финальный архив и проходит README без подсказок автора.

При регрессии вернуть автору Issue/PR с входом, командой, ожидаемым и фактическим
результатом, SHA и путём к журналу. Сохранённый RC1 не заменяется промежуточной
сборкой разработки; новый кандидат получает свою версию и новые измерения.

# Финансовая стресс-проверка

Из корня чистого checkout с установленным `requirements.lock`:

```sh
python tools/check_generalization.py --output artifacts/generalization
```

Команда заранее сохраняет 1 000 конфигураций и SHA-256 выбора, затем проверяет
каждую. Каталог результата должен быть новым. Входы используют профиль 1.1,
20 направлений между KZT/USD/EUR/JPY/KWD, 240/800/2 000 строк, 76/140/200 документов,
чистые истории, все четыре состояния двух взаимодействий и 4/8/12 ошибок.
Периоды включают високосный февраль и месяцы смены времени. Наличие такого месяца
само по себе не подтверждает покрытие повторяющегося часа: для него есть отдельные
контрольные финансовые примеры.

Для каждого входа независимый SQLite verifier получает только `public/`; его ответ
записывается перед чтением эталона. Сравниваются тип, затронутые сущности, сумма,
валюта и полный набор доказательств. Затем обычный `reconcile` проходит публичную
среду и оценщик, сохраняя настоящую траекторию. На каждом 25-м входе выполняется
повтор после переименования ID и перестановки строк: всего 40 пар при настройках
по умолчанию. Это автоматическая независимость реализаций, а не слепой ручной аудит.

`report.json` содержит SHA кода, признак изменённого checkout, версии, все seed/config,
хеши входов/ответов, оценки и ошибки. Снимки неуспешных случаев остаются в `failures/`.
Успешные снимки можно восстановить по сохранённой конфигурации; они удаляются после
проверки, чтобы не раздувать поставку. Если процесс оборвался, отчёт остаётся
`in_progress`, а не становится успешным. Любой провал даёт код выхода 1.

Этот набор служит диагностикой финансовой корректности. После публикации он не
является неизвестной контрольной выборкой. Политика здесь выполняется в процессе
доверенного тестового стенда: изоляцию, ресурсы, офлайн-поставку и конкурсный балл
эта команда не подтверждает. Их проверяет отдельная репетиция 4 × 20 + 20 пар.

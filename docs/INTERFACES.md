# Контракты первого среза

Авторитетные финансовые правила и закрытый режим описаны в [SPEC.md](SPEC.md). Типы Python для интеграции находятся в [contracts.py](../auditlab/contracts.py). Следующие функции — согласованные точки подключения для рабочих веток.

| Владелец | Публичная точка входа | Договор |
|---|---|---|
| GPT Pro 1 | `auditlab.generator.generate_episode(seed, config, output_dir)` | Создать неизменяемый снимок в новом каталоге с public/ и private/. Отдельные аргументы — seed и конфигурация. |
| GPT Pro 1 | `auditlab.environment.open_session(public_dir) -> PublicSession` | Метод inspect(action) обслуживает list_records, get_record, get_document, calculator. Возвращает ok и result либо ok=false и error. Чтение только публичных файлов. |
| Claude Pro 1 | `auditlab.runner.make_env(mode) -> Environment` | Runner оборачивает inspect и submit, один раз расходует шаг, прикрепляет remaining_steps, ведёт журнал, возвращает reset/step по ТЗ. Mode train или closed. |
| Claude Pro 1 | `auditlab.evaluator.score_submission(submission, truth, inspection_steps) -> Score` | Оценщик принимает JSON-объекты. Структурно ошибочная сдача фиксируется по ТЗ. truth — объект с episode_id и issues; поле допустимых наборов называется evidence_sets. |
| GPT Pro 1 / Claude Pro 1 | `auditlab.policies.make_policy(name, seed) -> Policy` / доверенный oracle | Имена публичных политик random, reconcile, flag_all. Новый экземпляр на эпизод. Oracle выполняет отдельный доверенный адаптер раннера. |
| Claude Pro 2 | `auditlab.verifier.verify_snapshot(public_dir) -> list[Finding]` | Воспроизводит результат по открытым данным; сопоставление с truth идёт вне этой функции. |
| Claude Pro 1 / Claude Pro 3 | Завершённый публичный экспорт | Каталог прогона: run.json (run_id, episode_id, policy, mode, status), public/ со снимком, trajectories.jsonl со строками формата §11, submission.json и score.json. Для демо доступны только завершённые открытые прогоны. |
| GPT Pro 2 | `python run.py verify`, `demo`, `replay` | Финальные команды собираются после подключения веток. На стартовом коммите проверка фундамента — unittest из README. |

## Публичная контрольная пара

Два небольших открытых разработческих примера находятся в fixtures/foundation/. В каждом эпизоде есть public/ с настоящими CSV/JSON/JSONL и отдельная private/ с открытым учебным эталоном. Загрузчик обычного аудитора получает только public/. Эти снимки предназначены для интеграции и не входят в 10 train и 10 dev. Условные локальные имена каталогов не передаются агенту. Индекс settlement_index перечисляет все движения по нераспределённому остатку до исключающей границы. Лишняя строка следующего месяца имеет значение как контекст. Для row_id в get_record используется локальный ключ, для цитирования — ledger/ROW. Денежные суммы в тиынах.

Синтетический платёж 50 000 ₸, первый зачёт 30 000 ₸. Второй зачёт 20 000 ₸ за минуту до границы закрывает обязательство. Зачёт через минуту после неё оставляет на отчётную дату расхождение 20 000 ₸ (2 000 000 тиын). У обоих дел одинаковые суммы и одинаковое число записей. Идентификаторы в разных эпизодах могут совпадать; поиск всегда ограничен текущим эпизодом.

## Дополнение интегратора: загрузка снимка и экспорт (срез 1.1)

Для сквозного теста доверенный вызывающий код сначала вызывает реальный
`generate_episode(seed, config, output_dir)`, затем `make_env("train")` и
`reset(seed, {"snapshot_dir": str(output_dir), "export_dir": str(run_dir),
"policy_name": "reconcile"})`. Снимок уже существует; runner не генерирует его
повторно и не меняет файлы. `run_dir` — новый, ещё не существующий каталог.
Иные конфигурации reset остаются в ответственности раннера.

Эти три поля — **доверенные настройки**, они не входят в observation/info.
Seed не передаётся обычному аудитору. Runner открывает PublicSession только на
`snapshot_dir/public`, а эталон передаёт исключительно оценщику. Начальное
observation содержит `manifest` и `remaining_steps=100`. `policy_name` используется
как метаданные экспорта; процесс политики получает только публичное наблюдение.

После финализации runner атомарно публикует описанный выше экспорт: `run.json`
со `status="completed"`, непустым уникальным run_id, policy, mode и episode_id,
`public/`, `submission.json`, `score.json`, `trajectories.jsonl`.
Усечённый или упавший опыт нельзя помечать completed. Формат журнала — ровно §11
SPEC; каждый записанный шаг соответствует фактически возвращённому step.
Существующий экспорт не перезаписывается. Это дополнение не меняет wire-действия
или версии финансовых схем `1.0`; согласованные изменения фиксируются в PR.

Исполнимые проверки: `tests/integration/test_components.py`. До поставки модулей
они имеют статус «не проверено». Сквозной тест пока выполняет политику в процессе
проверки и **не является проверкой изоляции** ISO-01/02/03; выпускной путь должен
перейти на изолированный адаптер Claude Pro 1. Независимой сверке передаётся копия
только public/, её ответ фиксируется до загрузки truth проверяющим кодом.


## Уточнения кандидата интеграции

Генератор 1.6 сохраняет опубликованный профиль `config_version: "1.0"` побайтно.
В профиле 1.1 манифест явно содержит `period_end_exclusive: true`; индекс
`policy.rule_versions` публикует версии правил, а строки `list_records(policy)`
дополнены полем `version`. `get_record(policy, fx_date/rounding)` сохраняет строковый
результат; версии отдельно доступны через `get_record(policy, rule_versions)`.

Runner 1.1 и evaluator 1.1 сохраняют публичные действия и формат результата.
Повреждённый закрытый эталон отклоняется до оценивания: одна финансовая причина
определяется парой `(type, canonical affected_ids)`, суммы строго целые неотрицательные
(без bool/coercion), каждый допустимый набор доказательств содержит 1–10 ссылок.
Ошибка эталона является ошибкой инфраструктуры, а не штрафом обычному аудитору.

Доверенная полнота сохранения и знаменатели внутренних измерений определены в
[MEASUREMENT_SEMANTICS.md](release/MEASUREMENT_SEMANTICS.md). Ошибка записи не
меняет финансовую награду, но не может считаться завершённым измерением.

### Проверяемая исходная книга (генератор 1.5, профиль 1.1)

Новые снимки профиля 1.1 сохраняют полную чистую книгу до мутаций в
`private/source_book/`: те же шесть форматов, что в `public/`, с собственным
`episode_id`, фактическими размерами и индексами расчётов до вмешательства.
`private/source_transition.json` содержит все изменённые строки `ledger`,
`invoices`, `payments`: `table`, `id`, `before`, `after`, `mutation_indexes`.
`null` обозначает добавление или удаление; индексы нулевые, адресуют
`provenance.mutations`. Один изменённый объект может относиться к нескольким
вмешательствам. Порядок строк не является изменением финансового содержания.

Закрытое поле `provenance.source_book` версии 1.0 связывает SHA-256 всех шести
исходных и конечных файлов, перехода и ID обоих снимков. Обычному аудитору эти
файлы, пути и хеши не передаются. `tools/check_source_books.py SNAPSHOT --output
report.json` проверяет хеши, полноту воспроизведения перехода, неизменность
первичных документов/курсов/политики, затем независимо считает обе книги через
SQL verifier по отдельным копиям только публичных файлов. Чистая книга должна
дать ноль выводов и замечаний; конечная — совпасть с truth, открываемым после
пересчёта. Старый профиль 1.0 не дополнен задним числом: для него этот отдельный
контроль возвращает `not_checked`, сохраняя все опубликованные байты.

В профиле 1.1 соседние курсы иногда дают один и тот же округлённый результат
(например, EUR 61 × 1.21 и × 1.22 дают JPY 74). Генератор 1.5 выбирает первый
более поздний курс в детерминированном 31-дневном цикле, который даёт ненулевое
расхождение. Выбор производится и для чистого состояния взаимодействия, поэтому
все четыре состояния имеют одну исходную книгу и согласованные курсы по датам.
Успешные прежние случаи с различимым курсом следующего дня сохраняют публичные
данные и truth. Профиль 1.0 и финансовые wire-схемы 1.0 не изменяются; новых
зависимостей нет. Эта проверка подтверждает внутреннюю методику команды, а не
официальный конкурсный балл.

### Сравнимые чистые и ошибочные случаи (генератор 1.6, профиль 1.1)

В генераторе 1.6 число однотипных первичных документов не зависит от числа
выбранных ошибок в трёх группах. `archive_copy` даёт шесть архивных пар, из
которых запрошенные дефекты получают второе признание. `split_payment` или
`next_day_settlement` дают шесть счетов с получением платежа на следующий день
и двумя движениями `UNAPPLIED`. В исходной книге каждый зачтён полностью. В
ошибочных случаях меняется сумма зачёта при прежних документах, времени и ID.
Запрошенные самостоятельные FX-ошибки при включённых отвлекающих случаях
выбираются среди шести однотипных оценок.

Есть законное признание счетов соседнего периода. При двух валютах сценарий
конверсии у границы виден и без включения взаимодействия, если заданы
отвлекающие случаи. Для маленьких диагностических конфигураций с явно
отключёнными отвлекающими случаями объём фона ограничен.

`next_day_settlement` остаётся допустимым только для профиля 1.1. Схема, API
и правила учёта прежние. Старые снимки 1.1 продолжают загружаться, для
побайтовой генерации прежнего 1.1 следует использовать зафиксированный коммит
генератора 1.5. Профиль 1.0 продолжает воспроизводить опубликованные файлы.
[Замеры и ограничения](reviews/generator-adversarial-v2/REPORT.md)

### Полный пропуск распределения (генератор 1.7, профиль 1.1)

`allocation_mode: "omitted"` задаёт полный пропуск для запрошенных
`issue_counts.payment_allocation`. Все назначенные платежи приходят до границы
периода. В исходной книге каждый из них полностью зачтён, а мутация удаляет
обе стороны проводки зачёта выбранного платежа. Остаток к отчётной границе
равен сумме платежа. Платёжный документ, его индекс проводок, проводка
поступления и публичное правило `policy/allocation` достаточны для расчёта.

Нулевое число ошибок с той же конфигурацией и seed создаёт чистый аналог.
В режиме `omitted` создаются шесть сопоставимых назначенных платежей. Порог
числа строк учитывает исходную книгу, а корректные казначейские операции
заполняют разницу. Опубликованные документы счетов и состав документов
платежей совпадают в паре. Индекс зачёта отражает фактические движения.

По умолчанию применяется `allocation_mode: "partial"`. Смешивание `omitted`
с `settlement_timing` или `allocation_fx_same_payment` отклоняется. Параметр
доступен только в профиле 1.1 и задаётся в конфигурации генерации.

## Runner 1.2 и evaluator 1.2: адаптер жюри Genesis

Подробно: [GENESIS_ADAPTER.md](GENESIS_ADAPTER.md). Публичные действия AuditLab, wire-схема `1.0`
и формат Score не меняются; изменения обратно совместимы и видны по версиям в доверенном отчёте.

- `judge_adapter.py` (корень, `/app` в образе runtime): `generate_episode`, `make_env`, `score_episode`
  по опубликованным определениям проверок 20.11.2026. Перевод конверта `{"name", "args"}` и
  наблюдений `{"result", "error", "remaining_steps"}` выполняется только в адаптере.
- `AuditEnvironment(..., rules="auditlab-1.1" | "genesis-2026-11-20")`; по умолчанию прежние правила.
  Новый доверенный ключ reset `started_at`: отсчёт срока от более раннего момента (вход в reset адаптера).
- Запрос оценщика может содержать `rules` и `public_dir` (по умолчанию соседний `public/`). Ответ
  правил по умолчанию сохраняет прежние поля; в `unmatched` возможна новая причина `unavailable_evidence`.
- Для обоих наборов правил: каждый указанный ключ доказательства должен быть доступен через
  `get_record` этого эпизода, иначе вывод — FP. При неоднозначности выбор по правилу организаторов:
  наименьшая последовательность `(issue_id, индекс вывода)`. TP/FP/FN от порядка выводов не зависят.
- Только `genesis-2026-11-20`: любая строка `type` и любая целая сумма структурно валидны и
  сопоставляются семантически (FP); эталон может содержать две ошибки с одинаковыми
  `(type, affected_ids)`; допуск суммы публикуется в `policy.json` как `matching_tolerance_minor`
  (по умолчанию 0). Невалидная сдача снаружи: `return=-1`, остальные метрики `null`; внутренний
  Score не меняется. Исторические результаты RC3 получены прежними версиями и не пересчитываются.

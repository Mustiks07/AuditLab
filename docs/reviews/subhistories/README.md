# Пересечение полных коммерческих историй внутри компаний

Проверка 20.11.2026: генератор 1.4, исходники `c89abe8`, программа
`internal-rehearsal-1.0`, опубликованные 10 train / 10 dev и 20 внутренних компаний.
[Исходный машиночитаемый результат](internal-1.0-generator-1.4.json) содержит точные
канонические документы, журналы, хеши и участников совпадений.

500 межнаборных сравнений целых компаний дали ноль совпадений family/book.
Дополнительная проверка выявила **две** одинаковые коммерческие истории dev/internal:

Совпали первичные условия, относительные даты выдачи/срока/платежей, позиции,
разрядности и все связанные стороны журналов. Это целые коммерческие цепочки,
а не одинаковая проводка. Обе истории чистые; названия зон и абсолютные периоды
различны (dev: декабрь 2026 / Almaty; internal-05: август 2027 / Kathmandu;
internal-02: май 2027 / UTC). Совпадение после нормализации не доказывает утечку
скрытого ответа, нарушение независимости всех компаний или успешность запоминания.
Оно ограничивает прежнее утверждение о непересечении: оно верно для целых компаний,
но не для всех содержащихся в них коммерческих историй.

Просмотрено 327 / 324 / 1164 контрагентских цепочек и 321 / 322 / 1137 цепочек
счетов в train / dev / internal. Train/dev и train/internal совпадений не дали.
Два совпадения найдены каждым из трёх видов (`counterparty`, `invoice`,
`posted_counterparty`). Пустые компании не создают фиктивного общего семейства.
Формат и пределы нормализации описаны в `datasets/README.md`.

Тесты диагностики сохраняют копию целой истории при изменении остальных дел компании
и переименовании ID, отличают иной номинал при том же правиле, различают первичку
и изменённый зачёт и не считают пустые компании общим коммерческим сюжетом.
Воспроизведение: `python -m datasets.audit_subhistories --output artifacts/subhistories.json`.
Результат зависит от опубликованной версии внутренней программы; этот файл хранит
исходное измерение до изменения её seeds. Старые релизные отчёты остаются историческими.

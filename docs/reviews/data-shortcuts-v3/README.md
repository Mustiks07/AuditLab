## Как устроена проверка

- **Три набора, результаты не смешиваются:**
  - A — опубликованные `datasets/open` train/dev: 20 эпизодов профиля 1.0, после склейки по происхождению 9 семей в dev;
  - B — профиль 1.2: 128 семей в 16 стратах, к каждой ошибочной — компания той же конфигурации с нулём ошибок, 232 эпизода;
  - C — `judge_adapter.generate_episode` с типовой конфигурацией: только `issue_counts` (версия по умолчанию 1.0) и то же с `config_version: "1.1"`, плюс `{}` и `{"config_version": "1.1"}`; 60 эпизодов.
- **Единица анализа — запись**: строка журнала, счёт, платёж. Метки: «относится к нарушению» и «входит в доказательства».
  - B: 115 328 записей, из них 894 относятся к нарушению и 351 входит в доказательства;
  - A: 6 320 записей;
  - C: 7 651 запись.
- **Признаки**, класс каждого задан до измерений:
  - искусственные — 23: префиксы и ранг ID, позиция строки, круглость, фиксированные отношения, минута/час/день, повторы сумм, размер журнала и контрагента, длина индекса, равные транши;
  - финансовый контекст — 3;
  - финансовое правило — мой независимый калькулятор.
- **Правило — один признак и один порог.** Подбирается по F1 только на исследовательских семьях (A — train; B и C — нечётные семьи) и один раз применяется к остальным.
- **На проверочной части показываются:** записи, положительные, базовая частота, precision, recall, подъём, отметки в чистых компаниях и бутстрэп-интервал по семьям (10 000).
- **Подтверждение** — пороги протокола на проверочной части плюс минимальный контрпример, воспроизведённый на свежих seed.

## Законный финансовый сигнал, а не подсказка

В профиле 1.2 правила «у платежа нет строки зачёта», «ни одного зачёта до границы» и «`settlement_index` из одной строки» дают precision 1,0 при recall 0,22. Свежие seed: 1,0 / 0,22, 0 отметок в чистых компаниях.

Программно проверено: на всех 6 618 платежах набора B эти правила отмечают ровно платежи, у которых весь назначенный остаток не зачтён до границы. Все отмеченные — нарушения (R7). Это и есть правило `policy.allocation` для полного пропуска, а не случайность генерации.

## Гипотезы (не подтверждены протоколом)

54 правила прошли пороги только на исследовательской части, либо имели < 20 положительных, либо подъём 3–10. Главные:
- A, счета: минута ≥ 59, час ≥ 23, день ≥ 30 — precision 1,0, но всего 9 положительных. Это тот же шаблон cutoff, что D1, на уровне документа;
- A и C: «один документ у контрагента», «4 строки у контрагента» — на свежих seed 0,09–0,17;
- C, платежи: час ≥ 19 → FX-нарушение, precision 1,0 на 12 и на 24 свежих положительных, но протокол требует ≥ 20 на проверочной части;
- B: `entity_rows == 4` — подъём около 5, precision ≤ 0,06.

Полный список — `findings` в отчёте.

## Проверки, которые ничего не нашли

- **Профиль 1.2, записи:** ID (префикс, длина, ранг), позиция строки в файле, круглость, фиксированные отношения, минута, секунда, час, день, повторы сумм, размер журнала — ни одно искусственное правило не подтвердилось, кроме D4.
- **Уровень компании, все наборы (R8):** число строк, документов, счетов, платежей, журналов, казначейских журналов, FX-строк, контрагентов — подъём около 1,0. Ни один счётчик не отделяет компании с нарушением от чистых.
- **Финансовое разнообразие профиля 1.2 (R5)** — 16 страт по 8 семей, всё passed. Для каждой страты по публичным проводкам подтверждено:
  - частичный пропуск с заданным числом траншей; поздний транш ровно на заданном смещении после границы, включая 0;
  - полный пропуск;
  - JPY (разрядность 0) и KWD (разрядность 3);
  - cutoff позднего признания и cutoff счёта следующего периода;
  - дубликат, FX, USD-база;
  - оба взаимодействия и две ошибки разных типов;
  - чистые финансовые случаи и чистые компании.

  Во всех 128 компаниях есть законные похожие операции: расщеплённый платёж, одинаковые суммы у разных покупателей, архивная копия, возврат с нулевым остатком. Мой независимый ответ совпал с эталоном.
- **Чистый контроль сохраняет историю (R6):** P9 passed во всех 13 ошибочных стратах — та же коммерческая история, нет находок, нет различающего простого признака из P9. D5 — признак, которого в P9 не было.

## Собственные ошибки, исправленные до публикации

- Для позднего транша я ожидал на один ранний транш меньше. По данным все `tranches` траншей стоят до границы, а остаток — один зачёт после неё. Исправлено, тест добавлен.
- Чистую пару взаимодействия allocation+FX я сначала строил без `interaction`, и P9 показал другую историю. Генератор принимает взаимодействие с нулём ошибок; с ним P9 проходит 8/8.
- Первая версия ставила «подтверждено» в наборе B без воспроизведения на свежих seed. Это нарушало протокол; добавлены свежие B и контрпримеры.
- Протокол требует подъём ≥ 10, а при базе > 10 % (свежий профиль 1.0) это недостижимо. Пороги не менялись; подтверждение A опирается на контрпримеры CE2 и CE3, как и требует раздел 5 протокола.

## Повтор на ветке Claude Pro 1

Интегратор проверяет ветку по фактам, а не по описанию PR:

```sh
git worktree add ../AuditLab-claude1 <ветка или SHA Claude Pro 1>
python review/data_shortcuts/run.py --checkout ../AuditLab-claude1 --out artifacts/shortcuts-claude1
python docs/reviews/data-shortcuts-v3/repro_v3.py artifacts/ce-claude1 --checkout ../AuditLab-claude1
```

Эпизоды строит генератор проверяемой ветки в отдельном процессе с её `judge_adapter`, анализ выполняет код этой ветки. Сравнить нужно `regressions` и `counterexamples.*.defect` с таблицей ниже (main `d745376`):

| ID | Свойство | main |
|---|---|---|
| R1 | профиль 1.2: нет подтверждённого искусственного правила | **failed** (D4) |
| R2 | адаптер с типовой конфигурацией: нет подтверждённого правила | **failed** (D3) |
| R3 | опубликованные train/dev: нет подтверждённого правила | **failed** (D1, D2) |
| R4 | профиль 1.2: чистая пара сохраняет число казначейских журналов | **failed** (D5) |
| R5 | профиль 1.2: каждая страта даёт заявленную ситуацию | passed |
| R6 | профиль 1.2: чистые пары проходят P9 | passed |
| R7 | сигнал пропуска совпадает с правилом распределения | passed |
| R8 | ни один счётчик компании не отделяет нарушения | passed |
| R9 | профиль 1.2: доля зачёта не фиксирована 3/5 | passed |

- Исправление считается принятым, только если соответствующая регрессия стала `passed`, а R5–R9 остались `passed`.
- Изменение опубликованных train/dev (R3) или профилей 1.0/1.1 нарушает их воспроизводимость. Возможно, правильнее не перегенерировать их, а сменить версию по умолчанию у адаптера или в документации жюри — это решение интегратора.

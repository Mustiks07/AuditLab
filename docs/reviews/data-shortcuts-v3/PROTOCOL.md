# Протокол проверки подсказок генерации v3 (Claude Pro 2)

`protocol_id`: `data-shortcuts-3.0`. База: `main` `d745376151febe51c01c997280a24832156b99cc`
(генератор 1.7 для профиля 1.1, 1.8 для профиля 1.2). Записан и опубликован **до** любых
измерений. Вопрос: можно ли находить нарушения и их доказательства по случайным особенностям
генерации, не выполняя финансовый аудит.

Статусы: `confirmed` (подтверждённый дефект), `hypothesis` (гипотеза), `nothing_found`,
`not_checked`. Внутренние показатели — не балл жюри.

## 1. Три набора, результаты не смешиваются

| Набор | Состав | Исследовательская часть | Проверочная часть |
|---|---|---|---|
| A. Опубликованные | `datasets/open/train` и `datasets/open/dev` как есть (20 эпизодов, профиль 1.0) | train | dev |
| B. Профиль 1.2 | новые эпизоды генератора 1.8, seed 9330001…, страты раздела 4; к каждому ошибочному — компания той же конфигурации с нулём ошибок | семьи с нечётным номером | семьи с чётным номером |
| C. Адаптер по умолчанию | `judge_adapter.generate_episode(seed, config)`, где config задаёт только `issue_counts` (один тип) и, отдельно, ещё `config_version: "1.1"`; чистые — `{}` и `{"config_version": "1.1"}`; seed 9340001… | семьи с нечётным номером | семьи с чётным номером |

- Семья — одно экономическое происхождение: seed и конфигурация (B, C) или общий исток по ≥ 50 % коммерческих цепочек (A).
- Ошибочная компания и её чистая пара всегда в одной части.
- Закрытый набор из 90 семейств **не используется**: ни для поиска, ни для настройки, ни для тестов. Его seed ≥ 10^9 по построению, а все seed здесь < 10^7.

## 2. Единица анализа — запись

Записи: строка `ledger`, документ `invoices`, документ `payments`. Для каждой записи две метки:
- `affected` — запись относится к нарушению: её `invoice_id` или `payment_id` входит в `affected_ids`;
- `evidence` — ключ записи входит хотя бы в один набор доказательств эталона.

Признаки и их класс заданы заранее:

| Класс | Признаки |
|---|---|
| **искусственный** (нет бухгалтерского смысла) | префикс ID (1–2 символа), длина ID, ранг ID среди отсортированных ключей таблицы, позиция строки в файле (доля, номер с конца), круглость суммы (нули в основных единицах), фиксированное отношение суммы к сумме связанного платежа или счёта (2/5, 3/5, 1/2, 5/8, 3/8), минута, секунда, час, день месяца, повтор суммы в таблице, совпадение времени с записью другого журнала, число строк в журнале, число документов и строк у контрагента, длина `settlement_index`, число `invoice_refs` |
| **финансовый контекст** (смысл есть, но доказательством не является) | расстояние до границы периода, повтор `canonical_key` или `invoice_id` у документов, отсутствие любой строки зачёта у платежа |
| **финансовое правило** (решает по политике) | остаток `UNAPPLIED` до границы > 0; расхождение FX-оценки с курсом даты события; повторное признание; признание вне периода документа |

Финансовые правила считает мой независимый калькулятор (`review/genesis_acceptance/independent_calc.py`). Это потолок законного сигнала, с ним сравниваются подсказки.

## 3. Эвристики, подбор и проверка

- Правило — один признак и один порог: `x ≥ t`, `x ≤ t` или `x == v`. Для таблицы, класса записей и цели (`affected` / `evidence`) правило выбирается по F1 **только на исследовательской части**. Затем оно один раз применяется к проверочной части.
- Отдельно — правило уровня компании: «в компании есть запись, отмеченная правилом» → «у компании есть нарушение».
- На проверочной части показываются:
  - число записей и положительных;
  - базовая частота;
  - precision, recall;
  - подъём (precision / базовая частота);
  - записи, отмеченные в чистых компаниях;
  - доля чистых компаний с хотя бы одним обвинением;
  - 95 % интервал precision и recall бутстрэпом по семьям (10 000, seed 20261122).
- Accuracy не используется как основание.

## 4. Финансовое разнообразие (набор B)

Страты: частичный пропуск (доля из seed), полный пропуск, 1–3 транша, последний транш за границей (`settlement_offset_minutes` 0 и > 0), cutoff счёта (до и после границы, `issued_next_period`), валюты с разрядностью 0 (JPY), 2 (KZT, USD), 3 (KWD), чистый возврат, взаимодействия allocation+FX и cutoff+FX, дубликат, FX, законные похожие операции (`split_payment`, `equal_amount_different_supplier`, `archive_copy`, `refund`, `next_day_settlement`), чистые компании.

Проверяется:
- что каждая страта действительно даёт заявленную финансовую ситуацию (по публичным проводкам);
- что чистый контроль сохраняет экономическую историю (P9 из `review/agent_generalization/pairs.py`: та же коммерческая история, нет находок, нет простого различающего признака).

## 5. Решающие правила

- **confirmed** — признак искусственного класса или финансового контекста на проверочной части даёт:
  - precision ≥ 0,5;
  - подъём ≥ 10;
  - recall ≥ 0,2;
  - не меньше 20 положительных записей;
  - нижнюю границу интервала precision > 5 × базовой частоты.

  Плюс минимальный контрпример воспроизводится заново с новым seed.
- **hypothesis** — выполнено только на исследовательской части; либо положительных < 20; либо подъём 3–10.
- **nothing_found** — иначе.

Признак финансового контекста засчитывается как подсказка только тогда, когда его precision на проверочной части выше, чем у законного финансового правила, или законные похожие операции его не встречают вовсе.

## 6. Контрпримеры, регрессии и повтор на другой ветке

- Для каждой подтверждённой проблемы сохраняются: вход (seed, конфигурация), команда, ожидаемый и фактический результат, SHA.
- Регрессионная проверка формулирует желаемое свойство («правило X на свежих эпизодах даёт precision ≤ базовая частота × 3»). На `d745376` она может провалиться — это и есть зафиксированный дефект.
- `review/data_shortcuts/run.py --checkout PATH` повторяет всё на любом checkout: эпизоды строит генератор этого checkout в отдельном процессе, анализ выполняет мой код. Так интегратор проверит ветку Claude Pro 1 по фактам, а не по описанию PR.

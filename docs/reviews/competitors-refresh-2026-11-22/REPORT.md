## 2. Важная коррекция предыдущей версии обзора

Предыдущая версия ошибочно трактовала `literal_pair_probe` как доказанный риск до 11,25 балла.
Полное чтение официальных правил и внутренних `ID_RULES` показывает обратное:

- Genesis требует согласованно заменять **все ID и все ссылки на них**, включая дополнительные
  документированные поля;
- официальный по смыслу преобразователь `value/discover`, который меняет ссылки внутри составных
  значений, AuditLab проходит 24/24 [код/CI];
- literal-преобразователь меняет только часть полей и оставляет старые ссылки. Это полезный
  отрицательный контроль на противоречивую копию эпизода, но не наблюдавшаяся процедура жюри;
- собственный N2 AuditLab прямо отмечает конфликт literal-трактовки с R2/R6.

Поэтому результат AuditLab 0/5 на literal-зонде **не конвертируется в потерю официальных баллов**.
Проекты с 5/5 лишь терпимее к неконсистентному преобразователю. Перед сдачей достаточно ясной карты
ссылок и проверяющей команды; рискованная миграция truth на сырые ID не обоснована.

## 7. Сильные стороны и реальные ограничения AuditLab

### Сильнее конкурентов

- независимый Genesis-стенд обязателен в CI, а ответ рецензента фиксируется хешем до открытия truth;
- hostile-политики, канал и Docker-лимиты проверяются как часть поставки;
- RC4/RC5 имеют receiver receipts на classic и containerd [авт., квитанции доступны];
- JPY 0 / KWD 3 знака, DST, ночные FX, clean twins и финансовые семьи дают более глубокий домен;
- ограничения и незавершённые A/B/C не маскируются маркетинговым баллом.

### Слабее или пока недоказанно

- нет измеренного улучшения агента;
- submission-материалы ещё не в `main` и не в RC5;
- база open-1.3 всегда KZT;
- OPS-01 (вся машина ≤4 ГБ) и OPS-02 (независимый получатель) самим проектом помечены как
  `not_checked`/внешние; не следует выдавать их за подтверждённые;
- автоматически скрывать ключ при `{}` нельзя без изменения семантики воспроизводимости. Нужен
  явный jury-private config и, при желании, fail-fast closed mode — именно это направление выбрано
  в PR #69.

## 8. Рекомендованный порядок действий

1. Дождаться зелёного CI PR #69, проверить свежим получателем, затем решить, как submission-файлы
   попадают к жюри: новый RC либо явно описанная пара «RC5 + Git materials».
2. Зафиксировать в инструкции карту ID/reference fields и проверку согласованной копии; не менять
   truth на сырые ID перед дедлайном.
3. После сдачи добавить маленькую обучаемую политику/детектор с sealed family split, noise/no-train
   контролем, clean false positives, временем и стоимостью. Прогонять её через публичный adapter.
4. Затем расширить генератор базовыми валютами и сделать один документированный hard-профиль,
   где простая политика заметно уступает обученной.
5. Возвращаться к LLM A/B/C только при гарантированной квоте, предрегистрации и запасном локальном
   варианте; нулевой submit не должен снова поглотить предсдаточное время.

## 10. Граница заимствования

Код конкурентов не копировался. В рекомендации перенесены только общие инженерные идеи: явная
submission-упаковка, обучаемая маломерная политика с контролями, hard-профиль и воспроизводимый
eval. Лицензии и происхождение кода нужно проверять отдельно перед любым заимствованием реализации.

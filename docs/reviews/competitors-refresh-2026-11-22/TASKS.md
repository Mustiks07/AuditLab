# Задания интегратору по итогам конкурентного аудита

Порядок учитывает официальный вес, риск регрессии и оставшееся время. Код продукта в ветке обзора
не менялся. PR #69 рассматривается отдельно: его изменения нельзя считать свойством `main` до merge.

## A. Риски сдачи и воспроизводимости

### A1. Завершить PR #69 и сделать submission-артефакт однозначным

- **Проблема и доказательство.** На `main`/RC5 нет полного корневого `trajectories.jsonl`, единого
  `docs/JURY.md` и однозначного указания, что материал §09 — `datasets/open-1.3`. PR #69 добавляет
  всё это, но открыт; RC5 после merge всё равно не изменится.
- **Требуемое поведение.** CI PR #69 уже зелёный; проверить его на свежем clone. Затем выбрать один
  из двух вариантов: выпустить новый RC с материалами или явно документировать, что жюри получает
  RC5 плюс конкретный Git SHA и root-level submission-файлы. Не оставлять два «главных» пакета.
- **Польза.** Закрывает наиболее вероятную операционную потерю по воспроизводимости (15) и
  инженерии (10), не затрагивая генератор или награду.
- **Компоненты/зависимости.** PR #69, README, `docs/JURY.md`, `datasets/README.md`,
  `trajectories.jsonl`, manifest, release notes/asset; владелец интеграции и выпуска.
- **Приёмка.** Чистый получатель по одной ссылке и одной команде: (1) видит ровно 10 train + 10 dev
  open-1.3, (2) валидирует root trajectories, (3) получает ожидаемый exit code, (4) сверяет SHA,
  (5) не обращается к сети. Все ссылки внутри пакета работают.
- **Риск регрессии.** Низкий для merge, средний для нового релиза. Не менять RC5 задним числом.

### A2. Явный закрытый ключ и fail-fast режим вместо неявного машинного секрета

- **Проблема и доказательство.** Без `episode_key` seed восстанавливается по публичному ID за 9,7 с
  в ограниченном пространстве [изм.]. Но автоматическая генерация постоянного локального ключа при
  `{}` сделает одинаковые `seed+config` разными на разных машинах и ослабит официальный якорь
  воспроизводимости. PR #69 уже добавляет helper для явной private-конфигурации.
- **Требуемое поведение.** Сохранить `{}` как детерминированный открытый режим. Для закрытого прогона
  использовать явный `episode_key`/config, не публиковать его и добавить опциональный
  `--require-private-key`/env guard, который падает до генерации, если ключ не задан. В provenance —
  только безопасный fingerprint.
- **Польза.** Одновременно защищает hidden episodes от перебора и сохраняет переносимость.
- **Компоненты/зависимости.** `make_judge_config.py` из PR #69, adapter CLI/runner, JURY doc, тесты;
  владелец adapter + независимый проверяющий.
- **Приёмка.** (1) одинаковый явный config побайтно одинаков на двух чистых машинах; (2) guard без
  ключа падает до записи файлов; (3) атака без ключа не находит seed; (4) ключ отсутствует в public,
  observation, logs и archive; (5) `{}` продолжает воспроизводить открытый профиль.
- **Риск регрессии.** Низкий, если guard opt-in; средний, если менять default.

### A3. Зафиксировать корректную семантику ID-transformer без миграции truth

- **Проблема и доказательство.** `literal_pair_probe` даёт AuditLab 0/5, но преобразует не все
  ссылки и противоречит официальному требованию согласованной замены. Correct value/discover
  transformer проходит 24/24. Прежнее утверждение «риск до 11,25 балла» отозвано.
- **Требуемое поведение.** Оставить формат truth. В JURY/INTERFACES перечислить все reference fields,
  пространства и составные значения; дать команду проверки копии и пример согласованной замены.
  PR #69 уже добавляет карту — проверить её на полноту.
- **Польза.** Снижает риск неправильной настройки жюри без высокорисковой миграции generator,
  matcher, UI, datasets и receipts.
- **Компоненты/зависимости.** `docs/JURY.md`, `docs/INTERFACES.md`, `ID_RULES.md`, checker; интегратор.
- **Приёмка.** (1) внешний consistent-transformer проходит 20/20 open episodes и 24/24 suite;
  (2) checker отвергает копию, где изменён ID, но не ссылка; (3) документация совпадает со схемой;
  (4) старые профили остаются побайтно неизменны.
- **Риск регрессии.** Низкий. Миграцию на raw ID перед сдачей не выполнять.

### A4. Проверить однокомандный путь именно из сдаваемого архива

- **Проблема и доказательство.** На `main` `python run.py verify` может корректно завершиться
  `incomplete`/2 из-за внешних OPS-01/OPS-02; это легко принять за провал. PR #69 разъясняет коды,
  но ещё не является release asset.
- **Требуемое поведение.** В первой инструкции жюри дать одну обязательную команду, ожидаемый код,
  время и границу между проверками кейса и внешней rehearsal. Проверять не рабочее дерево автора, а
  распакованный submission-артефакт без cache и сети.
- **Польза.** Предотвращает ложный отказ на инженерной проверке.
- **Компоненты/зависимости.** launcher, offline bundle, JURY, release workflow; release owner.
- **Приёмка.** Два свежих получателя (classic/containerd, если заявлены) получают одинаковый
  обязательный результат и понимают значение каждого non-zero кода.
- **Риск регрессии.** Низкий; средний только при изменении логики launcher.

## B. Существенные конкурентные преимущества

### B1. Небольшая обученная политика с честным контрольным экспериментом

- **Проблема и доказательство.** A/B/C AuditLab завершился 0 submit. Между тем azamxvit показал
  воспроизводимый logistic detector, ibrahimerbol — CEM, vouchai — REINFORCE, tryHard — SFT. Для
  демонстрации обучения необязательно начинать с внешнего LLM.
- **Требуемое поведение.** Обучить маломерную политику/классификатор только по публичным действиям и
  записям. Агент должен читать через adapter/tools и делать реальный `submit`; нельзя напрямую
  загружать private truth. Сравнить с `reconcile`, noise и no-training на sealed family split.
- **Польза.** Даёт проверяемый ответ на центральный вопрос защиты: чему агент научился и почему
  результат не равен ручному правилу.
- **Компоненты/зависимости.** `auditlab/research/agents`, public adapter, trajectory exporter,
  experiment manifest, offline evaluator; исследователь агента + независимый проверяющий.
- **Приёмка.** Предрегистрация; train/dev/test разделены по seed **и семействам**; указаны TP/FP/FN,
  return, clean false-positive rate, CI/разброс, время/CPU/RAM; артефакт модели и exact rerun SHA;
  повтор на чистой машине совпадает в заданном tolerance.
- **Риск регрессии.** Не включать в обязательный judge path до отдельной проверки. Средний риск
  leakage — нужен независимый аудит признаков.

### B2. Разнообразить базовую валюту в новом профиле

- **Проблема и доказательство.** В open-1.3 и проверенных default episodes база KZT. У ряда
  конкурентов опубликованы KZT/USD/EUR/GBP. Текущие JPY/KWD проверки сильны, но не демонстрируют
  разные base ledgers.
- **Требуемое поведение.** Создать профиль 1.4, выбирающий минимум две базовые валюты по seed;
  профиль 1.3 и RC receipts не менять.
- **Польза.** Усиливает данные/эталон (25) и переносимость финансовых правил.
- **Компоненты/зависимости.** generator profiles, FX/oracle, datasets, checker, console; generator owner.
- **Приёмка.** В 20 seed ≥2 базы; oracle и независимый checker проходят; minor-unit правила для
  0/2/3 знаков сохранены; контрольные политики не получают подсказку из префикса.
- **Риск регрессии.** Средний; только после сдачи.

### B3. Документированный hard-профиль с измеримым разрывом

- **Проблема и доказательство.** AuditLab имеет сложные семьи, но нет одной ручки и таблицы,
  показывающей, что простое правило ломается. У madiyar и ibrahimerbol такой контраст хорошо виден.
- **Требуемое поведение.** Собрать существующие ночные FX, clean twins, partial allocation и
  multi-currency cases в версионированный hard-profile. Сравнить oracle, reconcile и B1-policy.
- **Польза.** Делает финансовую глубину видимой и связывает её с обучением агента.
- **Компоненты/зависимости.** profile 1.4/hard, policies, experiment report; generator + research.
- **Приёмка.** Oracle без потерь; независимый checker зелёный; простой baseline статистически хуже
  на sealed test; no-leak и paired reproducibility проходят.
- **Риск регрессии.** Средний; не менять default до защиты совместимости.

### B4. Возобновить LLM A/B/C только с гарантированным планом выполнения

- **Проблема и доказательство.** Текущий A/B/C — полезный отчёт об ограничении инфраструктуры, но
  не эксперимент: quota/timeout, 0 submit. Повтор без изменения условий снова не даст эффекта.
- **Требуемое поведение.** До запуска проверить квоту и latency, иметь локальный fallback, малый
  smoke, checkpoint/resume и лимит времени. Сначала сравнить один LLM-вариант с B1-policy, затем
  расширять факторы.
- **Польза.** Экономит время и делает стоимость/качество измеримыми.
- **Компоненты/зависимости.** experiment runner, provider config, budget ledger, sealed dataset.
- **Приёмка.** У каждого arm есть ≥1 валидный submit до массового запуска; предрегистрация и
  stop-rule зафиксированы; отчёт отделяет provider failures от model quality.
- **Риск регрессии.** Высокая внешняя зависимость; только после стабильного детерминированного B1.

## C. Улучшения меньшего приоритета

### C1. Исправить смысл mutation-report, не «чинить пять ошибок оценщика»

- **Проблема.** Предыдущая версия обзора назвала пять `survived` невыявленными дефектами. По
  независимому отчёту основной evaluator совпал с oracle 299/299; Y1–Y6 убиты проектными тестами,
  а `survived` относится только к конкретной attack battery.
- **Изменение.** В отчёте вывести две отдельные оси: `killed_by_project_tests` и
  `killed_by_attack_battery`, плюс легенду для equivalent mutants. Добавлять граничные атаки можно,
  но не выдавать их отсутствие за известную ошибку production evaluator.
- **Приёмка.** Один JSON/Markdown однозначно показывает статус каждого мутанта и denominator.
- **Риск.** Низкий. Исполнитель: независимый assurance owner.

### C2. Публичное статическое демо на сохранённых открытых данных

- **Проблема.** Несколько конкурентов имеют доступный сайт; это не даёт официальных баллов, но
  ускоряет защиту. AuditLab сейчас требует локальный запуск.
- **Изменение.** Статическая сборка console с open-1.3 export, без backend, ключей и private truth.
- **Приёмка.** Страница открывается без сервера, содержит provenance и ссылку на exact dataset SHA.
- **Риск.** Низкий, после сдачи. Исполнитель: frontend/demo owner.

### C3. Автоматизировать ежедневный каталог конкурентов, но не их оценку

- **Проблема.** В последние часы сильные проекты менялись быстрее ручного отчёта.
- **Изменение.** Сохранять GitHub search results, SHA, pushed time и Actions status в JSON; новый
  код всегда требует ручного чтения и изолированного запуска.
- **Приёмка.** Повторная команда даёт diff кандидатов без потери старого SHA и не публикует
  самодельные score/rank.
- **Риск.** Низкий. Исполнитель: review automation owner.

## Не делать перед сдачей

- не переписывать truth на сырые ID ради literal-зонда;
- не включать неявный per-machine secret в default `{}`;
- не утверждать, что A/B/C улучшил модель;
- не называть self-check конкурента официальным баллом;
- не копировать код конкурентов без отдельной проверки лицензии и происхождения.

## А. Риски непрохождения проверок

### A1. Ссылки эталона, устойчивые к буквальному преобразованию ID (P06–P20, до 11,25 балла)

- **Проблема.** На буквальном преобразователе (переименованы только поля §03, ссылки эталона — непрозрачные строки) оракул AuditLab получает TP 3→0 на 5/5 эпизодах [изм.: `evidence/literal-pairs/AuditLab.json`]. Команда сама измерила то же (N2: 4/24, только чистые) — [jury-compatibility-v3](../jury-compatibility-v3/README.md). 13 из 16 адаптеров конкурентов на той же процедуре проходят 5/5 [изм.: `evidence/literal-pairs/`].
- **Изменение — минимум сегодня.** В README (раздел «для жюри») и `docs/demo/HANDOFF.md` одной таблицей перечислить все поля, несущие ID:
  - `affected_ids` = `invoice/<invoice_id>` | `payment/<payment_id>`;
  - `evidence_ids` = `ledger/<row_id>` и т. д.;
  - `payments.settlement_index.unapplied_row_ids` → пространство `row_id`;
  - `allocation_instructions`;
  - `journal_id` не переименовывается.

  Плюс правило: «переименовывайте значение и внутри составной строки после `/`». Указать самопроверку копии `python -m review.jury_compatibility_v3.check_links EPISODE_DIR` с кодами 0/1/2. Если это есть в поставке RC5 — дать путь; если нет — не обещать.
- **Изменение — полный вариант** (решение интегратора). Профиль правил Genesis, где `affected_ids` и `evidence_ids` в `truth.json` — сырые значения `invoice_id`, `payment_id`, `row_id`, `doc_id`. Пространства уже различимы по префиксам генератора `I`/`P`/`R`/`D`. Для FX — официальный ключ `date:source:target`, для правил policy — документированное имя. Внутренние правила `auditlab-1.1` остаются как есть.
- **Польза.** Ответ оракула не зависит от того, как жюри понимает «согласованную замену»; данные копии не становятся противоречивыми (условие 6 блока D).
- **Компоненты.** `auditlab/generator` (запись truth), `auditlab/evaluator/{schema,matcher,evidence}.py` (профиль `genesis-2026-11-20`), `auditlab/runner/genesis.py`, `review/genesis_acceptance`, `review/jury_compatibility_v3`, консоль (отображение ссылок), открытые наборы и квитанции.
- **Приёмка.**
  1. `evidence/literal_pair_probe.py` на AuditLab даёт 5/5 (и на 20 эпизодах open-1.3).
  2. Стенд Genesis в CI сохраняет 20/21/20/20/15/13.
  3. Внешний преобразователь по значениям сохраняет 24/24.
  4. Прежние снимки профилей 1.0–1.3 загружаются без изменения байтов.
- **Риск регрессии.** Высокий для полного варианта: затрагиваются эталон, matcher, консоль и все квитанции. Перед сдачей — только минимум.
- **Исполнитель.** Минимум — документация (интегратор). Полный вариант — владелец оценщика вместе с владельцем генератора, ревью независимого проверяющего.

### A2. Ключ закрытой генерации по умолчанию на стороне жюри

- **Проблема.** Без `episode_key` seed по одному публичному `invoice_id` восстанавливается за 9,7 с перебором 0…10⁶ при угаданном `{}` [изм.: `evidence/probe_auditlab.json`]. Документация это честно признаёт, но защита включается, только если жюри само передаст ключ в скрытой конфигурации. madiyar берёт ключ из `AUDITENV_SECRET`, а при отсутствии один раз создаёт случайный файл ключа жюри — README «For the jury», `auditenv/grader_key.py`.
- **Изменение.** В `judge_adapter.generate_episode`, если `episode_key` не задан явно, взять его из `AUDITLAB_EPISODE_KEY` или из файла ключа жюри (создаётся `secrets.token_hex(32)` при первом вызове, права 600, путь задаётся переменной окружения). В `provenance` записать только префикс SHA-256 ключа и источник. Явная конфигурация без ключа должна быть доступна флагом — для воспроизведения открытых наборов.
- **Польза.** Закрытая генерация защищена от перебора, даже если жюри не прочитает раздел про ключ. Повтор на машине жюри детерминирован: файл ключа постоянный.
- **Компоненты.** `auditlab/runner/genesis.py`, `auditlab/generator/profile13.py` (не менять схему), `docs/GENESIS_ADAPTER.md`, тесты адаптера.
- **Приёмка.**
  1. Два вызова `generate_episode(seed, {})` на одной машине дают побайтно одинаковые файлы.
  2. Атака из `evidence/probe_auditlab.py` без знания ключа не находит seed.
  3. Ключ отсутствует в `public/`, наблюдениях и журнале.
  4. Открытые наборы пересобираются явным режимом без ключа.
- **Риск регрессии.** Средний: открытые наборы и квитанции, сгенерированные через адаптер без ключа, перестанут совпадать, если не задать явный режим. Нужен один тест на совместимость.
- **Исполнитель.** Владелец адаптера (runner).

Команда регенерации в README и тест, сверяющий файл побайтно и проверяющий отсутствие ключей эталона в `observation`.
- **Польза.** Прямо закрывает материал §09 и пункт «траектории» на 2/2.
- **Компоненты.** `run.py` или `auditlab/runner` (экспорт), README, `tests/runner`.
- **Приёмка.**
  1. В файле ровно 7 полей на строку.

  3. Тест регенерации побайтно проходит в CI.
  4. `grep` по `expected_amount|evidence_sets|issue_id` в `observation` пуст.

### A5. Однозначная «одна команда» для жюри

- **Проблема.** README и SPEC §15 называют `python run.py verify`, но ожидаемый итог — `incomplete`/2 из-за внешних OPS-01 и OPS-02. По якорю инженерного критерия «документированная одна команда запускает проверку» получатель может принять код 2 за провал. - **Изменение.** В разделе «для жюри» явно указать одну команду, где exit 0 = «все обязательные проверки кейса прошли» (например `offline.py verify --suite quick`, если там это так), и отдельно — что `--require-complete` и `rehearsal` строже и почему дают 2. Логику не менять.
- **Приёмка.** Получатель по одному абзацу знает команду, ожидаемый код и время.
- **Риск.** Низкий. **Исполнитель.** Интегратор.

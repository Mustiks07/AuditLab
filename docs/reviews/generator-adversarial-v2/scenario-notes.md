# Дата проводки как заменитель проверки периода

## План до запуска

Исходный `main`: `daf1fc64df37651e14801e0286b9741b30820d35`. Фиксируем восемь seed `915231..915238` включительно. На каждом генерируем одиночный и связанный с FX случаи с четырьмя заранее определёнными состояниями. Контрольные профили, размеры, зоны и месяцы записаны в `scenario-probe.py`. Конфигурации не меняются по результатам.

Гипотеза: простое правило «дебет AR без платежа после исключающей границы» на генераторе 1.5 выдаёт доказуемые находки `period_cutoff`, ни разу не сравнив дату первичного документа с периодом. Используем публичные `list_records`, ссылку на счёт восстанавливаем только по `invoice_id`. Публичные прогнозы записываем до открытия truth. Оцениваем только класс `period_cutoff`, включая чистые эпизоды и FX без ошибки периода. Для семантического контроля изменяем выдачу выбранного счёта в соседнем периоде на дату фактической проводки, сохраняем публичный прогноз и отдельный ожидаемый ответ. Затем сверяем SQL и обычным `reconcile` через runner.

Второй тест записан до просмотра новой выборки. Детерминированный порог «минимум два валютных дебета AR за границей» проверяем на `915261..915276`: обе конфигурации с идентичным seed/контекстом, чистое состояние взаимодействия периода и FX и состояние с обеими ошибками, UTC, март 2028, 240 проводок, 76 документов. Счётчик игнорирует дату документа, номинал и курс. TP/FP/FN относятся к признаку наличия ошибки на уровне эпизода. Отдельно проверяем наличие общего числа строк у чистых и ошибочных эпизодов.

На второй матрице дополнительно проверяем усиленное правило «время дебета AR отличается от времени выставления». Оно использует первичку, но не сравнивает периоды. Для него считаем совпадения по `affected_ids`, не начисляем награду. На промежуточном коммите `3a66cbe` в тех же 32 эпизодах правило дало 16 TP / 0 FP / 0 FN. Это диагностика на уже выбранной выборке, а не новый неизвестный контроль. Регрессия добавляет правильное признание с задержкой в том же периоде.

## Воспроизведение и факт на 1.5

```sh
python docs/reviews/generator-adversarial-v2/scenario-probe.py build artifacts/cutoff-probe
python docs/reviews/generator-adversarial-v2/scenario-probe.py grade artifacts/cutoff-probe
python docs/reviews/generator-adversarial-v2/scenario-probe.py threshold artifacts/cutoff-threshold
```

Из корня checkout с lock-зависимостями. Для исходного измерения копируют скрипт в ту же директорию отдельного чистого checkout указанного SHA. Для кандидата используют другой новый каталог, исходные результаты сохраняют. Фаза `build` выполняет прогноз только по манифесту и двум таблицам публичного снимка. Фаза `grade` открывает truth; обычная проверочная политика не получает приватный путь. Локальные результаты на Windows/Python 3.12.14; песочницу Linux и ресурсный профиль эти команды не проверяют.

На 1.5 прогноз дал **24 TP / 0 FP / 0 FN** на 48 эпизодах. Повторяемые классы имеют по 8 эпизодов: одиночный cutoff и два взаимодействия с ошибкой периода дали по 8 TP, одиночный чистый, чистое взаимодействие и только FX не дали прогнозов. Это совпадение с настоящими требуемыми ссылками и суммами по matcher, а не просто видимый статистический сигнал.

Минимальный смысловой контроль на seed `915231`: счёт `invoices/DCFF268585A3BDD4A75A807D3` получен 29.02.2028 07:43, проводка `ledger/R7E38D1744F950EEB16546341` датирована 01.03.2028 16:17, граница 01.03.2028 00:00, всё UTC+05. Ошибка **4 962 700 тиын = 49 627 KZT**. В синтетической копии счёт законно выставлен и признан 01.03 в 16:17, срок оплаты сдвинут на дату выдачи +14 дней. Остальная книга и номинал сохранены. Прогноз по дате проводки дал один FP, SQLite verifier дал ноль находок и замечаний, реальный `reconcile` с публичными действиями завершился пустой сдачей, награда 0,984. Исторические SHA-256 `predictions.json` — `3d7f00ce6d3d2507f7b913c10028a71741943e0ff8716b4a9fc56856179b25f5`, `control-answer.json` — `d4d2aa0e2e0abaaf6d974394b8e8a93d9e51e00452ef0fa66bded860f2cb76aa`.

### Что улучшать дальше

- Реальные чистые признания после границы закрывают обнаруженное правило точного угадывания в измеренных конфигурациях. Использовать выборку, где наличие ошибки и число поздних строк разделены сильнее, полезно для дополнительной проверки. Счётчики, из которых можно получить вероятность класса, остаются риском для скрытых конфигураций.
- Полезная отдельная задача — добавить обратное смещение: источник в соседнем периоде, проводка внутри целевого. Ещё один вариант — относить движение CASH к месяцу по дате платежа. SQL уже проверяет оплату, обычный `reconcile` сейчас реализует cutoff для счета. Для расширения нужны отдельные согласованные тесты обоих путей. Точное время перехода DST для валютных событий тоже остаётся отдельным сценарием. Наличие месяцев с DST в этой матрице не измеряет повторяющийся или пропущенный час.
- Документы одной формы и повтор правила дебет AR/кредит REVENUE сами по себе ожидаемы. Выводы относятся к наличию метки и конкретному простому правилу на указанных выборках. Не проверены все комбинации признаков, скрытая программа жюри и обученная политика.

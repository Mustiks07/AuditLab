## Воспроизведённые проблемы

### P0 для генератора при новых сочетаниях валют

Вход `seed=0` и конфигурация

```json
{"config_version":"1.1","base_currency":"JPY","currencies":["JPY","EUR"],"clean_distractors":[],"interaction":"allocation_fx_same_payment","issue_counts":{"fx_conversion":1}}
```

Ожидается сгенерированный эпизод с одним наблюдаемым FX-расхождением. Фактически генерация останавливается до публикации с `RuntimeError: unintended_issue_counts`. Отказ воспроизведён для seed 0, 1, 5, 15, 16, 20, 23, 27, 29, 35, 38 из 0–39. У чистого близнеца того же seed сумма 61 EUR. Курс на 12 ноября 1,21 JPY за EUR даёт 73,81 → 74 JPY, а соседняя котировка 1,22 даёт 74,42 → те же 74 JPY. Разность округлённых сумм равна нулю. `_value` выбирает котировку следующего дня, добавляет дефект только при ненулевой округлённой разности, затем `Company.validate` требует ровно запрошенное число. [Курсы и мутация](../../../../auditlab/generator/scenarios.py#L92), [контроль числа](../../../../auditlab/generator/core.py#L258).

Влияние на кейс, стр. 2–5: допустимое сочетание параметров может прервать генерацию нового контрольного эпизода. Закрытая матрица организатора неизвестна. Владелец зоны Dataset/Simulator может выбрать публично существующую альтернативную котировку с детерминированно отличающимся значением после округления, либо подобрать согласованную шкалу котировок до фиксации первички для всех четырёх состояний. Приёмка отдельного PR: seed 0–39 для этого входа и матрица поддерживаемых пар валют и обоих взаимодействий. Во всех активных состояниях ровно один наблюдаемый FX-дефект, арифметика воспроизводится публичным verifier, чистый близнец чист, выключение соседнего дефекта сохраняет FX и общую первичку. Исторические train/dev сохраняют байты. Добавить один явный диагностический код для действительно неподдерживаемой комбинации.

### P1 для правдоподобия затруднений

Простой предиктор выбирает платёж, если задан один связанный счёт, индекс до границы содержит ровно две строки, а показанное местное время получения совпадает со временем выпуска счёта плюс ровно сутки. Ему достаточно `invoices.jsonl` и `payments.jsonl`, доступных также через `list_records`. Он не использует величины, содержимое проводок, FX или значения ID как признаки. Ответ зафиксирован до truth. [Публичные кандидаты](../evidence/finance-shortcut-public.json), SHA-256 `47fa4449d3476cd309bc564e4417a5bb14b2c90db8cf4b04b93fc5bf56885dcd`.

| Снимки | TP по ID платежа | FP | FN |
|---|---:|---:|---:|
| 10 опубликованных train | 3 | 0 | 0 |
| 10 опубликованных dev | 3 | 0 | 0 |
| 11 новых сгенерированных входов настоящей проверки | 5 | 0 | 0 |

Это диагностическое измерение кандидатов одного типа. Оно не измеряет F1 валидной отправки, сумму, доказательства, полный ассортимент конфигураций или закрытый набор. Создатель дефекта ставит receipt ровно через сутки после issue и сохраняет один из двух зачётов. У обычного чистого оплаченного счёта первая квитанция через двое суток, а сгенерированные чистые аналоги с сутками используют два зачёта и дают три строки индекса. Условия со связями сохранятся даже при простом переименовании ID. [Формирование платежей дефектов](../../../../auditlab/generator/core.py#L142), [чистые платежи](../../../../auditlab/generator/__init__.py#L122).

Приёмка отдельного PR зоны Dataset/Simulator: показать чистые платежи с тем же документным признаком (полный однократный зачёт после поступления на следующий день), дефекты с другими задержками и разбиениями зачётов, и одинаковый признак у нескольких пар с разными правильными ответами. Повторить диагностику на заранее отделённых новых семействах, сохранив разметку по фактической сверке из ledger. Конфигурации команды не следует засчитывать как скрытый контроль организаторов.

## Сильные стороны и пределы

- Профиль 1.1 сначала закрывает settlement indexes и валидирует книгу с пустым счётчиком дефектов, затем применяет отложенные строки на копии, пересчитывает индексы и снова валидирует. `Company.validate` проверяет ссылки, равновесие по валюте и журналу, сумму позиций, существование и предел evidence. `validation.py` независимо от формирования truth пересчитывает признания, назначения, FX и казначейство. Опубликованный совместимый профиль 1.0 использует прежний путь с немедленным изменением; требование «сначала вся чистая книга» на него нельзя распространять. В README и защите 1.1 должен быть явно выбран как путь для новых эпизодов. [Точка генерации](../../../../auditlab/generator/__init__.py#L325), [копирование книги](../../../../auditlab/generator/core.py#L112), [проверка](../../../../auditlab/generator/validation.py#L116).
- SQL verifier читает только публичный вход и не импортирует расчёты генератора. Движки исполняют одни SQL запросы и отличаются механизмом точного округления; согласие движков проверяет эти исполнения, а общую ошибку запроса способен обнаружить самостоятельный расчёт. Показательный предел наблюдаемости: даты разных котировок могут давать один округлённый результат. Правильный вывод тогда пуст, даже если закрытый план собирался использовать неверную дату. Формат также должен различать доказательство неверной оценки от предположения о точном внутреннем механизме ошибки. [Публичный загрузчик](../../../../auditlab/verifier/loader.py#L98), [SQL расчёт](../../../../sql/verifier/30_fx_conversion.sql), [два движка](../../../../auditlab/verifier/engine.py).
- Новые публичные ID непрозрачны и детерминированно назначаются отдельными потоками, порядок файлов перемешивается. Пользовательские действия сортируют записи по ID ради курсоров. В новых профилях варьируются суммы и даты, а чистые аналоги снижают тривиальные признаки «FX присутствует» и «архивная копия присутствует». Контрагентов представляют ID, строка позиции от генератора всегда `Commercial services`. Структура семейства может сохраняться при смене seed. Смена ID сохраняет корреляции графа и дат. [ID и первичка](../../../../auditlab/generator/core.py#L19), [шум](../../../../auditlab/generator/__init__.py#L138), [метаморфизм](../../../../auditlab/release/transforms.py#L38).
- Повторный `datasets.audit_families` подтвердил 500 сравнений целых историй (100 train/dev, по 200 train/internal и dev/internal), 0 межнаборных совпадений по семейному и бухгалтерскому отпечаткам. Одна преднамеренная пара внутри train и одна внутри dev найдены как семейства, не как одинаковые книги. Алгоритм исключает ID/порядок и группирует экономические события, сохраняя точные номиналы, даты и коммерческие связи. Он отвечает на вопрос равенства целой истории. Копирование одного общего кейса с другим фоном требует контрольной проверки на уровне подграфа основных фактов или предварительного разбиения по семействам сценариев. В этом исследовании фактического пересечения таких частичных историй не установлено и нет доказательства общего отсутствия утечек. [Определение отпечатка](../../../../datasets/audit_families.py#L27), [область применения](../../../../datasets/README.md#L103).
- Самый большой прогон здесь использовал публичный интерфейс на хосте Windows, включая отдельную SQL-проверку текстовых файлов. Ограничения Docker, Python 3.11, запуск 4 × 20 политик, 20 пар организатора, генерация отдельной операции KWD и метрики нового замороженного закрытого запуска здесь не проверялись. Старый независимый отчёт в `docs/reviews/manual-financial` покрывал открытый legacy, а интегратор отдельно сообщает 20 чистых автоматических SQL-проверок исходных книг. Наш опыт дополнительно покрывает большой вход, точную половину, повторяющийся час и обе матрицы. Для [#13](https://github.com/Mustiks07/AuditLab/issues/13) по-прежнему нужны оригинальные отчёты авторов и штатный экспорт полной исходной книги с хешем для доверенного проверяющего. Приёмка экспорта: новый получатель читает готовую книгу без перехвата, повторяет баланс и получает ноль находок до мутаций, затем повторяет причинную разницу по сохранённому соответствию строк. [Результаты интегратора](../../../reviews/integration-2026-11-20.md).

Конфигурации, seeds, семейства и хеши всех снимков закреплены в [recipe-1.3.json](recipe-1.3.json).
Проверка полного побайтового воспроизведения:

```sh
python tools/export_trajectories.py check
```

Все эти данные открытые: опубликованные seeds не являются секретами закрытой проверки.

и правила оценки.

## Исторический набор: open (dataset 1.1, профиль 1.0)

`datasets/open` сохранён без изменения байтов для воспроизведения прежних релизов
и контрольной пары интерфейса. Описание ниже относится именно к нему.


В `open/train` и `open/dev` по 10 синтетических эпизодов. Каждый набор содержит две чистые компании, четыре случая с одной ошибкой каждого типа, оба взаимодействия и два варианта смешанного пограничного случая. У каждой компании 240 строк проводок и 76 первичных документов. Имена каталогов совпадают с непрозрачными ID из публичного манифеста.

В `train` пограничная пара сохраняет независимый дубликат счёта. Последний зачёт проходит за минуту до границы или за минуту после неё. В `dev` пара сохраняет независимую ошибку периода и сравнивает зачёт за минуту до границы с зачётом ровно на ней. Каждая пара целиком входит в свой набор. Оба набора содержат чистую компанию с валютной оценкой. В `dev` используются JPY и KWD с разрядностью 0 и 3.

## Воспроизведение

Из корня репозитория с Python 3.11 или новее выполните команду с новым каталогом назначения.

```sh
python -m datasets.build build/open-datasets
python -m unittest discover -s tests/foundation -v
python -m unittest discover -s tests/simulator -v
```

`recipe.json` фиксирует версии, семейства, 128-битные seeds и конфигурации. Повторная сборка в другом каталоге создаёт те же относительные пути и байты. Доверенный код использует `datasets.build.build_datasets(output_dir)` для подготовки серии. Обычному аудитору передаётся `public/` конкретного эпизода. Организатор использует `private/truth.json` для оценки и `private/provenance.json` для воспроизведения.

Тест переносит только `public/` и через `open_session` находит платёж, счёт, правило и полный перечень движений. Остаток равен 0 ₸ при `before` и 20 000 ₸ при `at` и `after`. Значения в документах даны в тиынах. [Публичные инструменты и ключи](../docs/INTERFACES.md)

## Публичная сессия

`open_session(public_dir).inspect(action)` принимает `action` и `args` по контракту. `list_records` возвращает `records` и `next_cursor`. Передайте `cursor=null` для первой страницы и используйте полученный курсор для следующих. Допустимый размер страницы составляет от 1 до 50 записей. Доступны таблицы `ledger`, `invoices`, `payments`, `fx`, `policy`.

Для `get_record` используйте `row_id` в `ledger`, `doc_id` в `invoices` и `payments`, `YYYY-MM-DD/SRC/DST` в `fx` и имя правила в `policy`. Страницы `policy` содержат объекты `id` и `value`. `get_document` принимает `doc_id` счёта или платежа. В доказательствах добавляйте название таблицы, например `ledger/R72`. Правая граница `period_end` в манифесте исключается.

`calculator` возвращает десятичную строку. Допустимы десятичные числа, скобки и ASCII-операторы `+`, `-`, `*`, `/`. Длина выражения ограничена 256 символами, вложенность составляет до 24 уровней. Расчёт использует 64 значащие цифры и `ROUND_HALF_UP`. `remaining_steps` и `submit` обслуживает runner.

Валютная оценка публикуется отдельным журналом в базовой валюте. `FX_VALUATION` содержит оценку в `debit_minor`, `FX_OFFSET` содержит равный кредит. Обе строки ссылаются на один `journal_id`, контрагента и первичный документ. Если задан `payment_id`, `policy/fx_date` определяет курс по локальной дате и номиналу платежа. Для оценки счёта с пустым `payment_id` используются `issued_at` и `total_minor` счёта. Нативное признание и зачёт отражаются отдельно в валюте первичного документа.

## Конфигурация генератора

`generate_episode(seed, config, output_dir)` принимает целочисленный seed и создаёт новый каталог снимка. Параметры можно комбинировать.

Начиная с генератора **1.2**, новый профиль `config_version: "1.1"` предназначен
для внутренних проверок новых компаний. Он варьирует номиналы и даты дефектов
по seed, сохраняет общую основу четырёх состояний взаимодействия и добавляет
чистые аналоги пограничного признания и валютной оценки, когда включены
отвлекающие случаи. Суммы и даты сами по себе не являются метками ошибок.
Пара с `settlement_timing` сохраняет ручные 50 000/30 000/20 000 ₸.

Профиль `1.1` поддерживает максимум 12 дефектов, 200 документов и 2 000 проводок.
Размеры — минимальные цели, цель проводок округляется вверх до целой двойной
записи; итог не выходит за эти максимумы. Комбинация, чьи обязательные события
не помещаются, отклоняется до публикации. В частности, цели 2 000/200 дают
ровно 2 000 проводок и 200 первичных документов, включая дефекты.
Большие книги содержат также внутренние переводы `CASH ↔ CASH_RESERVE` в базовой
валюте. Они сохраняют суммарные денежные средства, не меняют зачёт платежей,
не требуют дополнительных внешних счетов/поручений и имеют `null` ссылки на
платёж и счёт. Это объявлено в `policy/accounts`; каждый перевод представлен
событием `treasury_transfer` в provenance. Валидатор проверяет его две стороны,
сумму, дату и отсутствие отрицательного остатка денежных счетов. Наборы
доказательств финансовых ошибок не раздуваются такими переводами.

Часовые пояса профиля `1.1` читаются из закреплённого пакета **tzdata 2026.6**,
независимо от системной базы IANA; версия записана в provenance. Для генератора
и обычной сверки нужен общий `requirements.lock`, включая tzdata.

Начиная с генератора **1.4**, профиль `1.1` строит всю исходную книгу, включая
первичку, зачёты, отвлекающие события и переводы. После проверки книги с пустым
набором ошибок применяет подготовленные изменения на копии, пересобирает
индексы зачёта и проверяет итог вместе с эталоном. В закрытом provenance
`source_book_validation` фиксирует число строк, документов и нулевое число
ошибок в исходной книге. Для побайтового повтора профиля `1.0` используется
прежний путь генерации.

Генератор **1.5** сохраняет эту полную книгу в `private/source_book/`, а не
только её агрегаты. Хеши исходных/конечных файлов и полный переход доступны
через `provenance.source_book` и `private/source_transition.json`. Проверка
получателя: `python tools/check_source_books.py SNAPSHOT --output source-check.json`.
Она независимо пересчитывает обе книги по публичным форматам и проверяет все
изменённые/добавленные/удалённые строки. Для старых снимков без книги возвращается
`not_checked`. Обычный аудитор по-прежнему получает исключительно `public/`.

Также 1.5 исключает неразличимые FX-мутации после округления: если ставка на
следующий день даёт ту же сумму в минимальных единицах, выбирается ближайшая
более поздняя ставка из неизменного 31-дневного расписания с ненулевым эффектом.
Этот выбор общий для чистого и испорченного состояний. Публичные данные и truth
успешных прежних случаев с различимым следующим днём сохранены. Оригинальные
160 файлов train/dev профиля 1.0 остаются побайтно прежними.

Генератор **1.3** добавляет в манифест профиля `1.1` явное
`period_end_exclusive: true`. `policy.rule_versions` объявляет версии всех
правил, включая строковые `fx_date` и `rounding`; у самого индекса также есть
`version`. Страницы публичной таблицы `policy` содержат `id`, `value`, `version`.
`get_record` сохраняет исходный тип значения правила; его версию можно получить
через `get_record(table="policy", id="rule_versions")`. Старые снимки без индекса
по-прежнему возвращают строки таблицы только с `id` и `value`.
Чистый сценарий `refund` содержит реальное получение незакреплённого депозита
и последующий возврат `debit UNAPPLIED / credit CASH`; отдельный тест профиля
проверяет источник, обе денежные стороны, нулевой остаток и отсутствие находок.

Старый профиль `config_version: "1.0"` (также значение по умолчанию) сохранён
для точного воспроизведения опубликованных наборов **1.1**; их файлы и эталоны
не менялись. Его provenance сохраняет версию генератора **1.1**. Следующая
таблица описывает этот совместимый профиль; ограничения нового профиля указаны выше.

| Поле | Допустимые значения |
|---|---|
| `config_version` | `1.0` |
| `target_period`, `timezone` | Месяц `YYYY-MM` и локальная зона, по умолчанию `2026-11` и `Asia/Almaty`. Для других зон, кроме `UTC`, используется системная база IANA. |
| `base_currency`, `currencies` | KZT, USD, EUR, JPY, KWD. Список уникален и включает базовую валюту. Для FX нужна иностранная валюта. |
| `issue_counts` | От 0 до 5 для `duplicate_invoice`, `payment_allocation`, `fx_conversion`, `period_cutoff`. Отсутствующее значение равно 0. |
| `interaction` | `allocation_fx_same_payment` или `cutoff_fx_same_invoice`. Счётчики выбирают активные дефекты. При нулевых счётчиках получается чистое состояние. |
| `settlement_timing` | `before`, `at`, `after` для пограничного зачёта. Для `at` и `after` нужен один дефект распределения. Если счётчик опущен, генератор задаёт его по времени зачёта. |
| `clean_distractors` | `split_payment`, `equal_amount_different_supplier`, `refund`, `archive_copy` |
| `company_size` | `ledger_rows_target` от 0 до 2 000 и `documents_target` от 0 до 600 задают желаемые минимумы. Целые проводки и документы могут повысить итоговый размер. |
| `snapshot_nonce` | Необязательное непрозрачное значение для различения независимых публикаций одного снимка. |

## Проверка пересечений экономических семейств

```sh
python -m datasets.audit_families
```

Проверка читает публичные документы `open/train` и `open/dev`, создаёт 20
эпизодов по зафиксированной внутренней программе и сравнивает все межнаборные
пары. Код возврата 1 означает совпадение. Ожидаемые пограничные пары внутри
одного набора перечисляются отдельно.

**Семейство 1.0.** Публичные ключи используются для связи контрагента,
коммерческого счёта, платежей и возвратов. В отпечатке сохраняются эти связи,
номиналы, валюты и их разрядности, даты выдачи, сроки, позиции счёта, принятые
платежи, суммы и даты возвратов. Моменты выражаются как смещения от начала
периода с учётом часового пояса. Одинаковые архивные копии одного счёта
сворачиваются. Отдельные счета с одинаковыми условиями сохраняются по одному
на коммерческий ключ. Отпечаток источника исключает публичные ID, порядок строк,
бухгалтерское отражение зачёта и признания, отчётные FX-оценки и внутренние переводы.

**Книга 1.0.** Второй отпечаток дополняет источники группами журналов и их
сторонами, бухгалтерскими датами, котировками и параметрами отчёта. Идентификаторы
и порядок строк по-прежнему исключены. Источники и связанные журналы сортируются
по каноническому JSON, затем для каждого отпечатка вычисляется SHA‑256.

Проверка охватывает форматы симулятора, где у платежа один счёт или пустое
назначение. Случай с несколькими назначениями или с журналом, связывающим разные
источники, даёт явную ошибку. Эта команда сравнивает компании целиком; она не исключает совпадения отдельных
коммерческих историй внутри разных компаний. Для них есть дополнительная диагностика:

```sh
python -m datasets.audit_subhistories --output artifacts/subhistories.json
```

Она сравнивает полный набор первичных счетов, связанных платежей и возвратов одного
контрагента, а также каждый полный счёт со всеми его платежами. Третий вид сохраняет
все связанные журналы, их стороны, базовую валюту и округление. ID и порядок удаляются,
даты нормализуются относительно начала периода; суммы, валюты, разрядности, сроки
и позиции сохраняются. Пустые компании и контрагенты только с казначейскими проводками
не считаются коммерческими историями. Совпадение одного правила или отдельной проводки
не достаточно. Глобальные FX-таблицы и название часового пояса не входят в частичный
отпечаток: их нужно учитывать при интерпретации совпадения. Произвольные частичные
подграфы и наборы вне выборки не проверяются. `--require-disjoint` возвращает код 1
при любом найденном совпадении полных коммерческих цепочек; обычный режим диагностический.

Исторические два совпадения чистых историй dev/internal и пределы вывода сохранены
в [отчёте](../docs/reviews/subhistories/README.md). Это не свидетельство утечки скрытых меток.

## Чистый контрпример к структурной эвристике

Для профиля 1.1 можно явно добавить `"next_day_settlement"` в
`clean_distractors`. Это полностью погашенный счёт с получением платежа через
один день после выставления и двумя строками `UNAPPLIED` (получение и полный
зачёт). Те же два внешних признака встречаются у незачтённого платежа; отличить
случаи позволяет финансовый пересчёт суммы. Опция не включается по умолчанию
и недоступна в legacy 1.0. Обычный `reconcile`, независимый SQL и проверка
исходной книги покрывают смешанные чистые/испорченные снимки на десяти seeds:

```sh
python -m unittest discover -s tests/simulator -p test_clean_counterpart.py -v
```

## Открытый набор 1.3 (генератор 1.9)

[`open-1.3/`](open-1.3) — отдельный выпуск. `open/`, `recipe.json` и `build.py` не менялись и
воспроизводятся побайтно. Рецепт [`recipe-1.3.json`](recipe-1.3.json): 128-битные seeds, конфигурации,
а для каждого снимка `episode_id` и SHA-256 дерева `public/`+`private/`.

| | train | dev |
|---|---|---|
| Чистые | 2: размеры по seed; 2000/200 | 2: размеры по seed; чистый двойник пограничного признания |
| Одиночные | дубль, частичный зачёт, FX, период | дубль, полный пропуск зачёта, FX в JPY, признание следующего периода |
| Взаимодействия | распределение+FX (оба), период+FX (только FX) | распределение+FX (только распределение), период+FX в KWD (оба) |
| Граница | три транша до границы, последний через минуту после неё | два транша до границы, последний ровно на ней |
| Смешанный | 2000/200, 5 ошибок четырёх типов | 2000/200, 6 ошибок четырёх типов |

Поля, отсутствующие в конфигурации, профиль 1.3 выбирает по seed+config: пояс, месяц, иностранная
валюта, размер, отвлекающие случаи. Seeds опубликованы, поэтому набор открытый. Защита от перебора к
нему не относится.

```sh
python -m datasets.build_13 build build/open-1.3      # новый каталог
python -m datasets.build_13 check datasets/open-1.3   # пересборка и побайтовое сравнение
python docs/reviews/generator-hardening-v3/verify_open_set.py --work build/v3-check --out build/v3-check.json
```
